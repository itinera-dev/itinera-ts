# itinera-ts: tier 1 plan

A general plan for implementing tier 1 of the Itinera specification in TypeScript, in this repository, itinera-dev/itinera-ts. Every decision listed under "Decisions" was taken with the maintainer on 2026-10-15 and 2026-10-16; on 2026-10-17 decision 8 was changed and decision 13 taken, and on 2026-10-19 decision 3 was changed, decision 10 changed, decision 4 confirmed, decision 14 taken as a default the maintainer may override, and tier 1 planned as one stack with the book as its last stage (sections 17 and 18). Stage 0 brought this file into the repository, as itinera-rs has its own.

Behaviour comes only from the [specification](https://github.com/itinera-dev/spec/tree/main/spec). Where this plan and the specification disagree, the specification is right. Code samples show the intended shape only; the tech specs record the final names.

## What this plan implements

- **Specification 0.1.0, tier 1**, checked by the conformance cases at **`v0.1.0-rc.16`**, the newest candidate, which adds the cases of proposals 0113, 0116 and 0119 to those of rc.15. That is 64 features and 357 scenarios.
- **The proposals**, 38 of them: 0002, 0003, 0008, 0009, 0010, 0011, 0012, 0024, 0027, 0032, 0040, 0041, 0042, 0049, 0054, 0055, 0056, 0057, 0058, 0060, 0061, 0062, 0063, 0064, 0065, 0081, 0083, 0085, 0091, 0095, 0098, 0102, 0104, 0106, 0113 and 0116, which make up tier 1, with 0113, value conversions, among them as the capability `value-conversions`; and 0108, test support, with 0119, which amends it, which count towards no tier and are listed only because this plan claims `testing`. Proposal 0111 has no cases: its suggested names are simply the names this plan uses, in camelCase.
- **Capabilities claimed:** `async` and `testing` (decision 1), and `value-conversions`, since itinera calls an application's `toValue()`, `fromValue`, guards and schemas while a journey runs (sections 2 and 3). The two `@capability-sync` scenarios do not run.
- **Rules made impossible to express:** five of the nine a conformance tag lets a language exclude, by TypeScript's types, each with a proof that the type check fails on. Three more are enforced at run time or when a class is defined, and their scenarios run, as do those of test support's five; the ninth, `mode-not-accepted`, does not arise (see "Rules made impossible, and rules enforced at run time").
- **When the cases move.** When the specification and conformance are tagged `v0.1.0`, once itinera-rs closes tier 1, a pull request moves `cases` to `v0.1.0`; any case changed after rc.16 gets a `spec update` issue, as PROCESS.md says.
- **Cases not yet merged.** Work that needs cases not yet merged in itinera-dev/conformance uses that pull request's branch until it merges and is tagged, for local runs only, while CI keeps running the tag pinned in `conformance.json`, and a proposal is listed only once its cases are at a tag.

## What carries over from Rust, and what does not

itinera-rs settled many questions that are not about Rust. This plan keeps those answers and changes only what TypeScript does differently.

| Rust's answer | In TypeScript |
|---|---|
| Macros are the API applications write, expanding to a public builder | Classes extending itinera's base classes, marked with decorators as close to the macros as the language allows, are the main way to declare. The decorators fill the lists of descriptors that a public builder reads, and the builder also puts a workflow together without decorators (section 4, decisions 2 and 11) |
| Traits and generated code tie the parts together | Abstract base classes, `Workflow`, `Step`, `RescueStep`, `StepPolicy` and `WorkflowPolicy`, which applications extend, give each subclass what it calls. The executor uses sealed classes of its own, which only itinera makes from what the decorators recorded, separate from the application's objects: a `WorkflowInstance` holds the workflow descriptor and the workflow object side by side, as Rust's does (section 5, decision 12) |
| The macro API was designed late, in stage 8 | The decorator API is designed in this plan, and each stage lands the decorators of what it adds |
| Nine rules made impossible by types, each proven by a compile-fail test | TypeScript, not JavaScript, is what itinera-ts supports, so whatever the types can refuse does not compile: five of the nine rules, each proven by a type test. Three are enforced at run time or when a class is defined, and their scenarios run; `mode-not-accepted` does not arise |
| One engine written as asynchronous code, driven synchronously with a waker that does nothing | One asynchronous engine. A promise cannot be driven synchronously, so a synchronous executor would need the engine written as generators (decision 1) |
| Values are `Serialize + Clone`; every receiver gets its own clone | Values are plain JSON data, or instances of classes that serialise themselves, turned into plain data when captured; every receiver gets its own copy (decision 5) |
| Reads name a Rust type; any other type is `wrong type` | Types are erased, so each request's type is a Standard Schema validator: the built-in schema the decorator metadata supplies where it is unambiguous, and elsewhere a written one, one of itinera's tokens, built on Zod, or any other; a class given to the builder without decorators writes each request's token by position (decisions 3 and 11) |
| Step statuses are private; the runner derives them from the events | The same |
| Decision logic is a pure function; the engine calls hooks around it | The same |
| One emitter assigns sequence numbers and timestamps, with a replaceable clock | The same |
| Guards around each reporter keep the failure rules whatever the dispatcher | The same |
| `Interrupted`, the executor's own signal, ends a step at its emit call | An executor-owned error class, never exported, thrown from the emit call: the journey-abort error, the same class through which a failing hook or reporter aborts the journey (sections 6 and 10) |
| `&mut self` makes concurrent journeys impossible to write | A run-time refusal when `run` is called while a journey runs, or with an instance that already ran |
| Panics are never caught | JavaScript has no unrecoverable failure that code can tell apart, so every throw is a recoverable failure and is caught |
| Conventional Commits with changelog trailers, git-cliff, merge commits, stacks per stage, a reviewer agent on every change | The same, from the first commit, except that tier 1 is one long stack, not a stack per stage (section 18) |

The four "Notes for other languages" at the end of the Rust plan all apply: a step's reporter is a small per-attempt object holding the dispatcher privately; the executor records the abort before throwing into a step, with the error class unexported; adapters may be found by reflection, which this plan does not need since decorators record them; and policies are rebuilt per attempt and per journey to keep hooks stateless.

## Architecture

### 1. Repository and packages

- **One published package, `itinera`**, the name free on npm today. It is one CommonJS build with a thin ESM layer that only re-exports it, so `import` and `require` both work, Jest included, and an application never loads two copies (the maintainer, 2026-10-16). It ships its own type declarations, and depends on `ts-results-es`, whose `Option` it re-exports from `itinera/option` and whose `Result` it uses only inside, never exporting it (decision 8), and `ts-pattern` (decision 10), and `zod`, on which itinera's type tokens are built and which it re-exports as `z` from `itinera/schema` (decision 3), with `reflect-metadata` as a peer dependency it imports itself (section 4). It has one subpath per concept, mirroring Rust's modules, as in `import { step, input } from "itinera/step"` for Rust's `use itinera::step::{step, input}` (decision 4). Test support is the subpath `itinera/testing`, so an application reaches it only when it imports it, as chapter 8, 8.1 point 2 asks; Rust puts it behind a feature in each concept's module, which a package cannot do.
- **An npm workspace** under `packages/`:

  | Package | Published | Holds |
  |---|---|---|
  | `itinera` | yes | Values and the data bag, events, reporters and dispatchers, the base classes and their decorators, the builder, the descriptors, the instance, the engine and the executor; `itinera/testing` |
  | `conformance` | no | The conformance runner, with its fixtures |

- **Runtimes.** The package uses only the language and the web platform's standard objects, such as `crypto.randomUUID`, never `node:` modules, so it runs on Node, Deno and Bun, and in browsers through a bundler, since the build is CommonJS. `reflect-metadata` adds a global polyfill. In a browser, `crypto.randomUUID` exists only in secure contexts, so the default journey ID needs one there, and the documentation says so. CI tests it on the supported Node versions only, Node 22 and later, and says so.
- **Modules follow concepts**, named with the specification's vocabulary, as in Rust: `error`, `value`, `journey`, `step`, `policy`, `event`, `report`, `service`, `workflow`, `instance`, `executor`, `option` and `schema`, each a subpath, plus `testing`, and the private `engine`, which is never exported. As Rust's crate root exports modules, not types, the package root exports nothing of its own.

### 2. Values and the data bag

- **A value** is plain JSON data: `null`, a boolean, a finite number, a string, an array of values, or a plain object (whose prototype is `Object.prototype` or `null`) with string keys. `undefined`, functions, symbols, `bigint`, `NaN` and the infinities, class instances, `Date`, `Map` and cycles are not values (decision 5).
- **A class that serialises itself** can be given wherever a value is expected: an instance with `toValue()`, whose class has a static `fromValue(value)`. It is turned into plain data once, by `toValue()`, when it is captured, so the data bag, events, reasons and global metadata hold only plain data. `fromValue` runs only for a request whose type is the class, named with `classOf` or supplied by the metadata, which gives the step an instance again. This is what Rust's `Serialize + DeserializeOwned` bound asks, made visible at run time.
- **One function captures a value**, at every point where something enters a journey: initial data, contributions, event data, a reason's details, global metadata, an adapter's value and a provider's data. It calls `toValue()` on any class that serialises itself, checks that the result is a value, and makes the copy that is stored, keeping a key named `__proto__` as a key, as `JSON.parse` does. It walks what it is given once, refusing objects whose prototype is not plain, such as a `Date`, and building the copy as it goes, so a getter is read once and what it returned is stored; it says where in what was given the first problem is (decision 9). `toValue()` is called at any depth, so a list of a class that serialises itself is captured as `classOf(C)` inside `listOf` reads it back (section 3).
- **What follows when it is not a value** is the specification's, where a language can express it:
  - a contribution, event data, a reason's details, global metadata set while the journey runs, and a provider's data abort the journey with `not a value`;
  - an adapter's value emits `input_adapter_failed` and aborts with `step could not be built` (chapter 4, 4.2 point 3.1);
  - initial data, and initial global metadata that is not a value or sets `journey_id`, are refused by `run`, listing each key. The one exception: a property of a plain object of initial data set to `undefined` is left out, as `#[derive(InitialData)]` leaves out a `None` in Rust.
  - A `toValue()` that returns what is not a value counts as giving a non-value, with the consequence above for where it was given. A `toValue()` that throws counts the same way, as proposal 0113 says of a value conversion that fails while a value is captured, so that initial data whose conversion fails is refused by `run` as not a value. From stage 1 a `toValue()` that throws while a value is captured, as a getter that throws does, makes it not a value, carrying no error, as the maintainer approved on 2026-10-19 and the proposal allows; reads follow in stage 5 (see "Points to watch").
- **Read-only when received.** Every input, data from the step or from the workflow and reason given to a receiver is its own copy, so changing it in place changes nothing else. Copies, not frozen objects: assigning to a frozen object throws in strict mode, which would turn a harmless change into an abnormal termination.
- **Types refuse what they can.** Wherever a value is expected, its type is `Value`, plain JSON data or `{ toValue(): Value }`, so functions, `undefined`, symbols, `bigint`, `Date`, `Map` and other objects with methods do not compile there. Types cannot refuse `NaN`, the infinities or cycles, so the run-time check stays, and the `non-value` scenarios run.
- **Absence is `None`.** An optional request gives an `Option`: `Some(value)` when present, a stored `null` included, and `None` only when absent, so the two can never be confused (decision 8).
- **The data bag** maps string keys to values and keeps keys in the order they were first set. A typed read, `data.read(key, type)`, whose type is a Standard Schema validator as a request's is (section 3), returns a `Read`, as Rust's does: present with the value, absent, or of another type, as chapter 4, 4.2 point 8.3 requires an adapter to be told; `read.option()` turns it into an `Option` when the difference between absent and another type does not matter. The data bag is a `Map`, as is global metadata, because a plain object moves keys that look like integers to the front, which would break "in the order first set" (chapter 2, 2.11 point 6) and the keys `journey_started` lists. Initial data and initial global metadata are accepted as a `Map`, as entries or as a plain object, and the documentation warns that a plain object reorders such keys.

### 3. Requests and their types

TypeScript's types disappear at run time, so the engine checks every value against a run-time description of the type its request asks for, and the compiler checks that description against the parameter's declared type (decision 3). There is one kind of description: every request's type is a Standard Schema validator, optionally wrapped in `optional(...)`, and the engine checks every request one way, through the Standard Schema interface. Each request gets its schema in one of three ways:

1. **From the metadata**, when the request writes no type. A request with no type compiles only when the parameter's declared type is exactly `number`, `string` or `boolean`, or a class with a static `fromValue`, never a union, a literal type, an enum or a branded type, which the metadata would record as a plain `Number` or `String`. The type the metadata supplies becomes the matching built-in schema, the token `number`, `string`, `boolean` or `classOf(C)`: `@input("amount") amount: number` checks for a number.
2. **From one of itinera's type tokens**, from `itinera/value`, written in the request, needed wherever the metadata records only `Object`, such as an interface, a union or an optional, or to narrow `number` to `integer`. Every token is a Standard Schema validator built on Zod, so itinera writes no type checking of its own beyond these tokens:
   - the neutral vocabulary of the cases, `string`, `integer`, `number`, `boolean`, `list` and `object`, each a Zod schema, where `integer` is `z.int()`, accepting a safe integer (`Number.isSafeInteger`), so a whole number beyond 2^53 minus 1 is `wrong type`, and `number` accepts any finite number, as `z.number()` does;
   - `listOf(token)` and `objectOf({ ... })` for shapes, Zod schemas built from the tokens they are given;
   - `optional(schema)`, which marks a request optional and takes any Standard Schema validator, a token or another library's. Optional is the engine's concern, not a check: an absent key gives `None` before any check runs, and only a present value is checked, by the schema `optional` wraps. It is not itself a validator but a marker the engine reads, from `itinera/value`, accepted only as a request's own type or a typed read's, never inside `listOf` or `objectOf`, where a Zod `.optional()` field is written instead;
   - `classOf(C)`, a Zod schema that carries the class `C`, whose static `fromValue(value)` makes an instance from a value and whose `toValue()` makes a value from an instance; once the stored value passes the check, the engine gives the step `C.fromValue(value)`, so that a step can contribute and receive a `Payment` with its methods while the data bag holds plain data;
   - `guard(name, isT)`, a Zod custom schema carrying its name, for an application's own check written as a type guard.
3. **From any other Standard Schema validator**, such as an application's own Zod schema, or a Valibot or ArkType one, written in the request in place of a token. The engine checks it exactly as it checks a token.

Whatever the schema, the compiler checks the parameter against the schema's input type, or against the class that `classOf(C)` carries, and the schema only checks: the step receives the stored value itself, never the schema's output, so a schema that coerces cannot turn a `wrong type` into a silent conversion. The one difference is a schema carrying a class, whose step receives what `fromValue` makes from the stored value. An optional request's parameter is checked against `Option` of the wrapped validator's type, and the engine applies `fromValue` wherever `classOf(C)` appears inside `optional`, `listOf` or `objectOf`. Any validator may be wrapped in `optional(...)`, so a request checked by a Valibot or ArkType schema may be optional too. A schema whose check is asynchronous cannot be used, since a read is synchronous; a Standard Schema validator shows that its check is asynchronous only by returning a promise when it runs, so it cannot be refused when its class is defined, and stage 5 refuses it when it reads a value (see "Points to watch").

**itinera re-exports Zod.** `zod` 4, whose release today is 4.6.7, is a runtime dependency, re-exported as `z` from the subpath `itinera/schema`, so an application writes `import { z } from "itinera/schema"` and installs nothing of its own. Its reason, which the tech spec of 0062 repeats, as the agents' manual requires: it gives the tokens their checks, their shapes and their Standard Schema interface, so itinera writes no type checking of its own, and it ships CommonJS and ESM builds with types for both, which the single CommonJS build needs. The documentation recommends importing `z` only from `itinera/schema`, so that the application uses the same copy as itinera: an ESM application importing `zod` directly loads its ESM build, a second copy beside the CommonJS one itinera loads. Any other Standard Schema validator, Zod from another copy included, is still accepted in a request.

What follows when a `fromValue`, a guard or a schema the application wrote refuses a value, or throws, is what proposal 0113 says of a value conversion that fails while a value is read: the value is of the wrong type, `wrong type` for a request and `other type` for a typed read of the data bag. Its abort may carry the conversion's error; itinera's carries none. Stage 5 implemented it (see "Points to watch"), and the tech spec of [0113](specs/0113-value-conversions.md) records it.

A class given to the builder without decorators writes the token or schema of each request by position, since no metadata is involved there; a decorated class given to it keeps its decorators' requests (section 5). Since itinera's tokens are Standard Schema validators, wherever this plan speaks of a request's token, the builder's tokens by position included, any other Standard Schema validator may stand in its place.

A request that writes no type where the metadata records `Object` or `undefined`, as a circular import gives, or where there is no metadata, throws when its class is defined, naming the parameter. A value that fails its check is `wrong type`, whether the request is required or optional, as chapters 4 and 6 say; a check made by custom code is the open point above. The suggested names of chapter 4, 4.11 point 2 follow: a required request gives the value, an optional one an `Option` of it.

Writing no type at all, with every type read from the declarations, needs a build tool that reads the source with the TypeScript compiler: decorators cannot, and TypeScript 7 runs no compiler plugins. A generator, `itinera generate`, writing the tokens of every request that lacks one into a file of plain TypeScript, is left for after tier 1; it changes no decorator.

### 4. The public API: base classes and decorators

Decided with the maintainer (decisions 2, 7, 11 and 12, 2026-10-15 and 2026-10-16):

- Decorators are the main API applications write, as close to Rust's macros as TypeScript allows, giving way to another form only where the language makes one impossible.
- TypeScript, not JavaScript, is what itinera-ts supports, so whatever TypeScript can refuse does not compile.
- The design is object-oriented: applications extend abstract base classes, which give them what they call, and the executor uses sealed classes that only itinera makes, separate from the application's objects (decisions 12 and 15).
- Decorators are the main way to declare. Under them, a public builder puts a workflow together from lists of descriptors, which the decorators fill when their classes are defined. Applications that do not use decorators declare their workflows with the builder, and so does the conformance runner (section 5, decision 11).
- The decorators are TypeScript's legacy decorators, which applications turn on with `experimentalDecorators`, as NestJS, TypeORM and Angular projects already do, with parameter decorators. `emitDecoratorMetadata` is required for the decorators, and supplies the type of a request that writes none (section 3).
- `Orders.build(...)`, a static method of `Workflow`, is how an application makes the workflow object it runs. It is the short form of `Orders.builder().constructWith(...).build()`, for a workflow that adds nothing through the builder.

The whole surface is planned here, and each stage lands the decorators and the builder methods of what it adds (section 17).

#### What a decorator can do, compared with a macro

A Rust macro generates code when the program compiles. A TypeScript decorator generates nothing: it is a function that runs once, when its class is defined, which is when its module is first imported. A legacy decorator can mark a class, a method or a parameter and record what it declares. It cannot add a member to the class's type or see a parameter's name. It could add a method to a class at run time, but TypeScript never changes a class's type because of a decorator, so the plan relies on no such method: what an application calls comes typed from the base class, and what the engine calls lives on the workflow descriptor (decision 12).

What a decorator cannot do, a base class does: it gives every subclass members on its type. So the two share the work:

1. **The base classes** give each subclass what Rust's macros generate for the application to call: `this.succeed()` and `this.fail(reason)` on a step, `this.keepDefault()` on a step policy, `this.supply(value)`, `this.fromDataBag()` and `this.provide(service)` on a workflow, `instance(...)` on a workflow, as `Orders::builder()` in Rust, and the static `build(...)`, `builder()` and `listing()` on a workflow class (section 5). A base class cannot be constructed, so every step, policy and workflow is a subclass. A workflow class inherits none of the engine's methods, which live on its workflow descriptor, so an application cannot override one by accident, though TypeScript has no `final` (decision 12).
2. **The decorators record**, and the class decorator checks what spans several members, throwing `Violations` when the class is defined: the counterpart of a macro's compile error, caught by any test that imports the module.
3. **What the types check, does not compile when wrong.** A legacy class decorator sees its class's type, and a legacy method decorator sees its method's type, so most mistakes are compile errors (section 5). A legacy parameter decorator sees its class, its method and its parameter's position, so it is typed against the parameter's declared type: a parameter whose type does not match its request does not compile (section 5).

#### The orders example of itinera-rs, in TypeScript

The same workflow as `crates/itinera/examples/orders.rs`, to show how close the two are. Names and modules follow Rust's, in camelCase.

```ts
import { type Contributor, contributor, type DataBag, dataBag, type JourneyId, journeyId } from "itinera/journey";
import { fromStep, onStepSuccess, onWorkflowSuccess, type OnSuccess, role, StepPolicy, stepPolicy, WorkflowPolicy, workflowPolicy } from "itinera/policy";
import type { Event } from "itinera/event";
import type { Reporter } from "itinera/report";
import { type Provided, provider, service, serviceType } from "itinera/service";
import { type Attempt, attempt, input, type Outcome, Step, step } from "itinera/step";
import { integer, optional, string } from "itinera/value";
import type { Option } from "itinera/option";
import { fromWorkflow, idGenerator, inputAdapter, type Supplied, withStep, Workflow, workflow } from "itinera/workflow";
import { LocalExecutor } from "itinera/executor";

/** Takes payments: the service a charge is paid through. */
interface PaymentGateway {
  take(amount: number): string;
}
const PAYMENT_GATEWAY = serviceType<PaymentGateway>("PaymentGateway");

/** The shop's card terminal, lent to one attempt to charge. */
class Terminal implements PaymentGateway {
  constructor(private readonly shop: string, private readonly attempt: Attempt) {}
  take(amount: number): string {
    return `${amount} paid at the ${this.shop} terminal, attempt ${this.attempt}`;
  }
}

/** Charges the amount the workflow's pricing works out. A charge of nothing is declined. */
@step()
class Charge extends Step {
  constructor(@input("amount", integer) private readonly amount: number) {
    super();
  }

  run(@service("payments", PAYMENT_GATEWAY) payments: PaymentGateway, @contributor() contributor: Contributor): Outcome {
    if (this.amount <= 0) return this.fail("declined");
    contributor.contribute("payment", payments.take(this.amount));
    contributor.contribute("charged", this.amount);
    return this.succeed();
  }
}

/** Ships the order. */
@step()
class Ship extends Step {
  run(): Outcome {
    return this.succeed();
  }
}

/** Notes each amount charged. */
@stepPolicy({ name: "audit" })
class Audit extends StepPolicy {
  @onStepSuccess()
  audited(@fromStep("charged", integer) charged: number, @contributor() contributor: Contributor): OnSuccess {
    contributor.contribute("audit", `charged ${charged}`);
    return this.keepDefault();
  }
}

/** A role the shop provides: telling a customer something. */
interface Messages {
  tell(message: string): void;
}

/** Tells the customer once the order is paid and shipped. */
@workflowPolicy({ name: "notify" })
class Notify extends WorkflowPolicy<Messages> {
  @onWorkflowSuccess()
  paid(
    @journeyId() id: JourneyId,
    @fromWorkflow("charged", integer) charged: number,
    @fromWorkflow("payment") payment: string,
    @role<Messages>() messages: Messages,
  ): void {
    messages.tell(`order ${id}: paid ${charged}, ${payment}`);
  }
}

/** Prints each event of every journey. */
class Printer implements Reporter {
  report(event: Event): void {
    console.log(event.journeyId, event.kind);
  }
}

@workflow({ name: "orders", policies: [Notify], reporters: [Printer] })
@withStep(Charge, { name: "charge", retryBudget: 1, policies: [Audit] })
@withStep(Ship, { name: "ship" })
class Orders extends Workflow implements Messages {
  constructor(private readonly shop: string) {
    super();
  }

  tell(message: string): void {
    console.log(`${this.shop}: ${message}`);
  }

  /** Works out the amount to charge: the price, less any discount. */
  @inputAdapter({ steps: ["charge"] })
  pricing(
    @fromWorkflow("price", integer) price: number,
    @fromWorkflow("discount", optional(integer)) discount: Option<number>,
  ): Supplied {
    return this.supply(price - discount.unwrapOr(0));
  }

  /** Lends each attempt to charge the shop's card terminal. */
  @provider(PAYMENT_GATEWAY, { perAttempt: true, steps: ["charge"] })
  payments(@attempt() attempt: Attempt): Provided<PaymentGateway> {
    return this.provide(new Terminal(this.shop, attempt));
  }

  /** Names each journey after the shop and the order. */
  @idGenerator()
  orderId(@dataBag() data: DataBag): string {
    return `${this.shop}-${data.read("order", string).option().unwrapOr("unknown")}`;
  }
}

const executor = new LocalExecutor();
for (const order of [{ order: "1", price: 40, discount: 5 }, { order: "2", price: 10, discount: 10 }]) {
  const result = await executor.run(Orders.build("corner").instance(order));
  console.log(result.journeyId, result.status.kind);
}
```

#### Every Rust macro and its counterpart

| Rust | TypeScript | Why it differs, when it does |
|---|---|---|
| `#[derive(Step)]` on a struct, with `#[input]`, `#[input("coupon")]` and `#[default]` fields | `@step()` on a class extending `Step`, whose constructor parameters carry `@input("amount", integer)` or `@input("coupon", optional(integer))`; its other fields are its own | A parameter's name is not available at run time, so the key is always written. The type is a Standard Schema validator: the built-in schema the metadata supplies for `number`, `string`, `boolean` and classes that serialise themselves, and otherwise a written one, a token such as `integer` or any other validator |
| `#[step]` on the block holding `run(self, #[service] payments: &dyn T, contributor, reporter)` | the `run` method, which `Step` declares abstract, its parameters marked `@service("payments", T)`, `@contributor()` and `@stepReporter()` | `Step` checks at compile time that `run` returns an outcome |
| `new(...)` building the step from its needs | the constructor, which may throw (`step could not be built`) | |

#### Where decorators are impossible, and what applications need

1. **Keys.** A parameter's name is not available at run time, so every request that Rust keys by a field's or a parameter's name has its key written.
2. **Functions.** Decorators exist only on classes and their members, so every step, policy and workflow declared with decorators is a class. The builder takes steps and policies as classes too, never as a loose function as Rust's closure steps are: a class extending itinera's base class, with or without decorators, so that the base class's protected helpers make its outcomes, lifecycles, supplied values and provided services exactly as they do for a decorated class (section 5). The workflow is still a class extending `Workflow`, whose static methods the builder is.
3. **Compiler options.** Applications that use the decorators turn on `experimentalDecorators` and `emitDecoratorMetadata`, and every application turns on `strict`, or at least `strictNullChecks` and `strictFunctionTypes`, without which several of the refusals of section 5 compile. A type-level guard makes the decorators fail to compile without `strictNullChecks`. `reflect-metadata` is a peer dependency that itinera imports itself, as NestJS does, so an application never has to import it first.
4. **Compilers.** TypeScript 5.5 or later (decision 14; 7.0.2, the native compiler, compiles these decorators and records their metadata), and swc, Bun and Deno with the options. esbuild, and so plain Vite, Vitest and tsx, compiles the decorators but records no metadata, so it cannot build an application that uses them: such applications use `tsc` or swc, and Vitest through its swc plugin, as NestJS projects do, or declare their workflows with the builder, which needs no metadata (section 5). The documentation says so in its first lines about decorators.
5. **Projects on the standard decorators**, with `experimentalDecorators` off, cannot use these decorators, since a project compiles one kind or the other. Supporting them as well is option 3 of decision 7, kept for when someone asks.

#### How the decorators are tested

- **Type tests** check every refusal at compile time of section 5 with `@ts-expect-error`, and include the proofs of the rules made impossible.
- **Unit tests** check what is recorded, every check made when a class is defined, and the check of parameter types against the metadata.
- **The conformance runner** builds every scenario's workflow with the builder (section 14), and its fixtures, written by hand, drive the cases' own sentences through workflows declared with these decorators as an application would, as Rust's `@macros` features do.

### 5. Under the decorators: registration and the descriptors

How a declaration is recorded, checked and used:

1. **Parameters.** Each parameter decorator records its request with the class, the method (or the constructor) and the parameter's position, in a private table inside itinera. Nothing is added to the class.
2. **Methods.** Each method decorator records the method's kind, with its options, in the same table. Parameter decorators run before their method's decorator, and the metadata is attached before either, so the method decorator sees all of them.
3. **Steps and policies.** `@step`, `@rescueStep`, `@stepPolicy` and `@workflowPolicy` gather what their class's members recorded, check it, and record the class's declaration: a step's needs and its run requests, or a policy's name and hooks with their requests.
4. **The workflow.** The decorators of a workflow class fill its lists of descriptors, the parts of a workflow descriptor: step descriptors, workflow policies, reporters, input adapters, service providers and the ID generator. Roles need no list, since they exist only in the types (section 7). Each `@withStep` adds a step descriptor: its step class, name, retry budget, whether abnormal terminations are retried, policies and rescue step. An input adapter, a service provider or the ID generator is recorded as a reference to the method its decorator marked, such as `Orders.prototype.pricing`, with its requests. `@workflow`, on the top line, runs last. It adds the workflow class's marked methods and its own options to the lists, puts the steps back in written order, checks every violation of chapter 3, 3.6 that the types do not rule out, and builds the class's `WorkflowDescriptor` object once, when the class is defined, storing it in a private registry keyed by the class. Every violation found is thrown at once as `Violations`. No decorator generates code or adds a member to the class: each only records what it marks, and the descriptor is an object of its own (decision 12).
5. **The builder** (decision 11). `Workflow` has two public static methods, `build(...args)` and `builder()`, in which `this` is the derived class:
   1. `Orders.build("corner")` reads the lists the decorators of `Orders` filled, takes the workflow descriptor made from them, and calls the `Orders` constructor with `"corner"`. The compiler checks the arguments against that constructor, as `ConstructorParameters<C>`, and `Workflow.build()` does not compile, since the base class is abstract. This is how an application makes the workflow object it runs, and it is the short form of `Orders.builder().constructWith("corner").build()`, for a workflow that adds nothing through the builder.
   2. **How `build()` hands the descriptor to the workflow object.** `build()` passes the application's own arguments, given to the static `build(...args)` or to the builder's `constructWith(...args)`, straight to the derived class's constructor, `new Orders(...args)`; the base class's constructor takes nothing and does nothing. `build()` then calls the base class's `#init(descriptor)`, an ECMAScript private method, so no application code can call or override it, and a derived class's own `init` does not clash. `#init` stores the checked workflow descriptor on the workflow object, in a private field, and marks the object as runnable; `instance()` later puts the two side by side in the `WorkflowInstance` (point 6). The static `build()` calls `#init` directly, being inside the class. The builder, a separate class, reaches it through a function that `Workflow.builder()`, inside `Workflow`, hands the builder's constructor, `(made, descriptor) => { made.#init(descriptor); }`; the builder's class is exported as a type only, so applications cannot make one with a function of their own. `Workflow` never has a public `attach`. `instance()`, a public method of the base class, reads `this.#descriptor` and returns a public `WorkflowInstance`, whose `descriptor` property the executor reads, so the executor never touches the private field. Verified on TypeScript 6.0.3. `build()` returns the object typed as built, `Built<Orders>`, through a `unique symbol` only itinera can name, and `instance()` takes `this: Built<this>`, so `new Orders("corner").instance(order)` does not compile. Should a cast get past the compiler, `instance()` checks the mark and throws, saying to use `Orders.build()`, so every instance `instance()` makes holds a checked descriptor; and `run` rejects with a `TypeError` an instance that `instance()` did not make, which only a cast lets through (point 7). Verified: TypeScript 6.0.3 compiles and runs it, and 7.0.2 type-checks it.
   3. `Orders.builder()` starts from the same lists and adds to them: step descriptors, workflow policies, reporters, input adapters, service providers and the ID generator. It keeps no list of roles (section 7). A step descriptor has a builder of its own, for its name, its requests, its retry budget, whether abnormal terminations are retried, its step policies and its rescue step, as itinera-rs's `StepDescriptor` has, started by the step class's static `builder(name)`: `Orders.builder().step(Charge.builder("charge").retryBudget(2))`. DECIDED (the maintainer, 2026-10-19): a builder per step, as itinera-rs has, not the one options object stage 3 settled. The builder's `constructWith(...args)` takes the derived class's constructor arguments, typed `ConstructorParameters<C>`, so `constructWith(3)` does not compile for `constructor(shop: string)`, and holds them until `build()`: `const orders = Orders.builder().constructWith("corner").build();`. The builder's `build()` takes no arguments. It makes a new workflow descriptor from the lists, checks it whole for every violation, as `@workflow` does, and throws `Violations`; only then does it call `new Orders(...args)`, then the base class's `#init(descriptor)`. The builder's type carries whether it is ready: for a class whose constructor needs arguments, `build()` does not compile until `constructWith` was called, and a class whose constructor takes none may call `build()` straight away. In Rust the workflow's struct is initialised before its builder is asked for; here the descriptor is checked before the object exists, and `#init` runs after it is made, so the builder holds the arguments. Verified: TypeScript 6.0.3 runs it, and 7.0.2 type-checks it. So a workflow put together through the builder is checked when `build()` runs, while one declared only with decorators is still checked when its class is defined.
   4. **What the builder takes: classes and methods, never loose functions.** Every step, rescue step and policy given to the builder is a class extending its base class, `Step`, `RescueStep`, `StepPolicy` or `WorkflowPolicy`; a reporter is a class implementing `Reporter`, as in `@workflow`'s `reporters`; an input adapter, a service provider or the ID generator is a method of the workflow class, which extends `Workflow`. Each base class has an ECMAScript private `#` field, so only a real subclass fits its type, and a class that merely has the same members, such as one with a `run` method that does not extend `Step`, does not compile. A class without decorators gives its tokens by position, with no metadata involved: `needs`, one token per constructor parameter, and `run`, one per parameter of `run`, each typed against the parameter it stands for, so a token that does not match does not compile. For example, `Orders.builder().step(Charge.builder("charge").needs(input("amount", integer)).run(service("payments", PAYMENTS))).constructWith("corner").build();` compiles only for a `Charge` extending `Step` whose constructor takes a number and whose `run` takes what `PAYMENTS` names (CHANGED in stage 4, for the maintainer to confirm: each token by position is the request decorator itself, since a type alone cannot say which request a parameter makes, see "Points to watch"). A policy names the method of each hook with its kind and its tokens, one per parameter, and an adapter, a provider or the ID generator its method with its tokens, in the same way, typed as the decorators type them, return type included. The base classes' protected helpers, such as `this.succeed()`, `this.keepDefault()`, `this.supply(value)` and `this.provide(service)`, make outcomes, lifecycles, supplied values and provided services exactly as they do for a decorated class. A class declared with decorators may be given too, its decorators giving its tokens. Verified for steps on TypeScript 6.0.3 and 7.0.2.
   5. **Naming.** The builder has `.name("orders")`. A name given there replaces the one `@workflow` gave, since the builder makes a new descriptor. When neither `@workflow` nor the builder named the workflow, the builder's `build()` throws, saying the workflow has no name.
   6. **Listing.** The static `Orders.listing()` lists what the decorators of `Orders` declared, and the builder has its own `.listing()`, which lists what it has put together so far. Both read a workflow descriptor, so they list alike, and neither needs a workflow object.
   7. The builder is public. Applications that do not use decorators declare their workflows with it, including those built with esbuild, Vite or tsx, which record no decorator metadata. Decorators remain the main way, and still need `emitDecoratorMetadata`.
   8. The conformance runner builds every scenario's workflow with it (section 14), and `itinera/testing` may use it for scripted runs (section 13).
6. **The types the executor uses**, named with the specification's words: `WorkflowDescriptor`, `StepDescriptor` and `PolicyDescriptor`, and `WorkflowInstance` for the instance (decision 12). Each is a class only itinera makes (point 7), `PolicyDescriptor` too once it lands.
   1. **The workflow descriptor is its own object**, separate from the application's workflow object, as in itinera-rs, where `WorkflowInstance` gives the executor `descriptor()`, the `WorkflowDescriptor<W>` the macros generate, and `workflow()`, the application's `W`, side by side. `@workflow` builds it once, when the class is defined, and the builder's `build()` builds a new one (points 4 and 5). It holds its name, step descriptors, workflow policy descriptors and listing, and references to the methods the decorators marked, such as `Orders.prototype.pricing`, or that were named to the builder. It calls them with the workflow object as `this`, so `this.shop` and `this.supply(...)` work in them.
   2. **`Workflow` does not implement `WorkflowDescriptor`.** An application class shows only the static `build()`, `builder()` and `listing()`, `instance()`, and the protected helpers `supply`, `fromDataBag` and `provide`. It inherits none of the engine's methods, so none can be overridden by accident, though TypeScript has no `final`, and the helper `provide` no longer shares its name with a method the engine calls.
   3. **The descriptor's methods take the workflow object** as their first argument where they call into it, as Rust's do. The members, whose exact signatures the tech spec of 0062 settles: `name`, `steps()`, `policies()`, `reporters()`, `adapt(workflow, step, key, access)`, `provide(workflow, step, service, key, access)`, `generateJourneyId(workflow, data)` and `listing()`.
   4. **The instance holds both.** `#init(descriptor)` stores the descriptor on the workflow object (point 5), and `instance()` puts the descriptor and the workflow object side by side in the `WorkflowInstance`, whose members are `descriptor`, `workflow`, `initialData`, `journeyId`, `takeReporters()` and `takeGlobalMetadata()`. The engine reads `instance.descriptor` and passes `instance.workflow` to the descriptor's calls.
   5. A `StepDescriptor` builds a step for an attempt, as `new Charge(amount)`, and runs it with its run requests. A `PolicyDescriptor` says which hooks it defines, builds an instance, and calls a hook by its kind, finding the method its decorator marked. The engine never looks a method up by name, except `run`.
7. **Descriptors and instances are sealed** (decision 15). `WorkflowDescriptor`, `StepDescriptor` and `WorkflowInstance` are classes with ECMAScript private `#` fields and private constructors, exported as types only, so only the decorators, the builder and `instance()` make one, each from a checked declaration. An object or a class written by hand with the same members does not compile where one is expected, and `run` rejects with a `TypeError` an instance that `instance()` did not make, which only a cast lets through. Every descriptor is then checked when it is made, so `run` checks none for violations. Chapter 5, 5.9 point 2 asks that any executor run any instance of the language, and names producing one by hand among the ways it may be produced; and leaves how that abstraction is expressed to each language; itinera-ts expresses it as sealed classes, so every instance the language allows is one `instance()` made, from a descriptor the decorators or the builder made, and the executor runs every one of them. Chapter 3, 3.7 point 2 asks `run` to check a descriptor only where an implementation does not guarantee that it was checked when it was built; a sealed, frozen descriptor, reachable only through a frozen instance, carries that guarantee. The documentation presents them as the engine's contract, not as a way to declare.
8. **Inheritance.** In tier 1, a declared class extends its base class directly: `@workflow` refuses a class whose parent is not `Workflow`, and likewise for the others. Inheriting declarations can be added later without breaking anything.

What is refused, and when:

| When | What |
|---|---|
| At compile time | A parameter whose declared type does not match its request, an optional request included; with the builder, a part that is not a class extending its base class, tokens that do not match the parameters they stand for by position, arguments to the static `build()` or to `constructWith()` that do not match the workflow class's constructor, the builder's `build()` before `constructWith()` for a class whose constructor needs arguments, `Workflow.build()` itself; and `instance()` on a workflow object that `build()` did not make, such as `new Orders("corner").instance(order)`; a hook, adapter, provider or `run` returning what its kind may not; a step hook on a workflow policy, or the reverse; a request on a parameter of a class that may not make it, such as `@fromStep` in a workflow policy; `@role<R>()` in a policy that does not name `R`; a policy whose roles the workflow class does not implement; a rescue step that skips; a write through an adapter's access to the data bag; a provider returning anything but `this.provide(...)`; a decorator on a class that does not extend its base class |
| When the module loads, from the metadata | A request of a decorator that writes no type where there is no metadata, naming the class and the option to turn on, or where the metadata records only `Object`, naming the parameter whose type must be written |
| When the class is defined | Every other violation of chapter 3, 3.6, such as two steps with one name, an adapter naming a step the workflow does not have, or `@attempt()` on a provider of journey scope; a request a hook's kind may not make, such as the cause in `on step success`; a request an input adapter, a provider or the ID generator may not make, such as `@contributor()` on an adapter or `@dataBag()` on a provider, since all three are methods of the workflow class; a parameter with no request; a step class not declared with `@step`; a decorator above `@workflow`; a class declared twice |

| When `build()` runs, for a workflow put together through the builder | Every violation of chapter 3, 3.6 in the new workflow descriptor, all checked whole and thrown at once as `Violations` before the constructor runs; and a workflow that neither `@workflow` nor `.name(...)` named, which throws saying so |
| When an instance is made | A workflow object that `build()` did not mark as runnable, which a cast got past the compiler: `instance()` throws, saying to use `Orders.build()` |

Everything in the last five rows happens before any journey, so throwing there keeps the rule that nothing escapes `run`. The metadata supplies the type of a request that writes none, only where the declared type is unambiguous (section 3); everywhere else the compiler checks the written schema, a token or any other validator, against the parameter.

Notes for the tech spec, from the reviews of this plan:

1. A legacy method decorator is generic in the method's type, since `TypedPropertyDescriptor<M>` is invariant.
2. A workflow hook is typed `void | Promise<void>`, since a method returning a value fits a bare `void`.
3. The roles a policy names live in a public or symbol-keyed phantom member, since a `protected` one lets every workflow pass.
4. Errors from overloaded decorators read "No overload matches this call", so the decorators avoid overloads where they can and the documentation lists the usual causes.
5. A parameter with no request is found from the length of the metadata's parameter types where there is metadata. A `run` with no decorated parameter has none, so it falls back to `Function.length`, which misses parameters with defaults and rest parameters; the documentation says so.
6. A parameter decorator is typed through its target's method and its literal position, `Parameters<T[K]>[I]`, or `ConstructorParameters<C>[I]` for a constructor. This cannot reach `protected` methods, so hooks, adapters, providers and `run` are public.
7. The roles a policy names are a covariant phantom, `declare readonly [roles]: R`, and `StepPolicy` and `WorkflowPolicy` carry distinct brands, since otherwise each is structurally the other.
8. The compiler's own message for a mismatched parameter is cryptic, so the types carry a readable reason, such as a string literal type naming the mismatch.

### 6. Steps

What section 4 declares, a step receives exactly: its inputs in its constructor, then its services, a contributor and a step reporter in `run`, already typed. A step class given to the builder without decorators receives the same, its tokens given by position, and is built for each attempt in the same way (section 5).

- **Requests resolve in the order written**: the constructor's parameters, then `run`'s.
- **Built once per attempt.** The engine makes the step with `new` for each attempt, giving its constructor its inputs. The constructor may throw (`step could not be built`). Nothing carries over between attempts.
- **Outcomes**: `this.succeed()`, `this.fail(reason)`, `this.skip()` and `this.skipBecause(reason)`, where a reason is a code alone or `{ code, message, details }`, as chapter 6, 6.11 point 2 suggests. `Step` declares `run` abstract, returning an outcome or a promise of one, nothing else, so a step without `run`, or returning anything else, does not compile. A step reports something abnormal by throwing, never by returning an error (decision 8). Anything `run` throws, or what still comes back through `any` or a cast, is an abnormal termination, carrying the thrown error, with one exception: the journey-abort error of the executor's signal, below, aborts the journey instead.
- **Handles belong to the attempt.** The contributor and the step reporter are made for the attempt and closed when it ends. A call on a closed handle runs nothing, changes no journey, and throws where it is made, synchronously, as chapter 4, 4.6 point 7 says it should.
- **Emitting is awaited.** `reporter.info`, `warning` and `error`, each with optional data, and `setGlobalMetadata`, return promises, since reporters may be asynchronous. Every call on a step's handles goes through one queue, so a step that does not await an emit still gets the specification's order: the engine settles every call the step started before it records the outcome. The documentation recommends the `no-floating-promises` lint rule to applications.
- **The executor's signal.** The engine records the abort at once, and the call that caused it ends the step or hook by throwing the journey-abort error, of a class the package never exports, carrying the abort reason and, when custom code failed, the error it threw: an emit or an entry of global metadata on which a reporter failed, event data or global metadata that is not a value (chapter 2, 2.9 point 4), global metadata that sets `journey_id` (`reserved metadata key`), and a contribution that is not a value, which throws synchronously since `contribute` returns nothing. It is the same class as the error the wrapper around hooks and reporters throws (section 10), so when a reporter fails on a step's emit, the error the wrapper throws is the one the emit call throws into the step. When the journey-abort error comes out of `run`, or out of a hook, the engine aborts the journey instead of recording an abnormal termination. Since the abort was recorded when the error was thrown, whatever the step does afterwards is ignored: a step that catches the error and returns an outcome, or throws something else, still ends the journey aborted, with no outcome fact and no commit.
- **No unhandled rejections.** Node ends the process on a rejected promise that nobody handles, so the engine attaches a handler that does nothing to every promise it hands to custom code. A step that awaits the promise still sees the rejection; one that does not cannot crash the application.
- **Rescue steps** extend `RescueStep` and are declared with `@rescueStep()`, with the extra requests `@fromRescuedStep(key, type)`, `@failureReason()` and `@error()` on its constructor's parameters. `RescueStep` offers only `this.succeed()` and `this.fail(reason)`, and its `run` must return one of them or a promise of one, failing by throwing as a step does, so a rescue step that skips does not compile. If a cast returns a skip anyway, the engine aborts the journey with `rescue skipped`.

### 7. Policies, hooks and roles

- **Two kinds of policy**, classes extending `StepPolicy` or `WorkflowPolicy`. A step hook's decorator compiles only on a method of a `StepPolicy`, and a workflow hook's only on a method of a `WorkflowPolicy`, so a policy with hooks of both kinds cannot be written.
- **Each hook marks its parameters** with what its kind may request: data from the step, the step's name, the attempt, the failure reason and the error for step hooks, and the cause for `on step failure` and `on step retry` only; data from the workflow, the journey ID, roles, a contributor and a hook reporter for every hook. A request that only step hooks may make does not compile in a workflow policy; one that only some step hooks may make, such as the cause, is refused when the class is defined, since a parameter decorator cannot see its method's decorator.
- **Each hook returns its own type**: `OnSuccess` for `on step success` (`this.keepDefault()`, `this.finishWorkflow()`, `this.failWorkflow(reason)`), `OnFailure` for the three failure hooks (`this.keepDefault()`, `this.failWorkflow(reason)`), and nothing for workflow hooks, as chapter 6, 6.11 suggests. A hook returns that, or a promise of it, nothing else, and fails by throwing, `hook failed` (chapter 5, 5.10), never by returning an error (decision 8); the engine calls it through the wrapper of section 10. The hook decorators type what the method returns, so a failure hook returning `this.finishWorkflow()` does not compile. The engine still checks what actually came back, since `any` or a cast slips past the types: `undefined` means the default (chapter 6, 6.3 point 1), and anything else a hook may not return aborts the journey with `invalid lifecycle`. Input adapters and providers likewise return their own type, a supplied value or "from the data bag", or a provided service, or a promise of it, and the ID generator returns a journey ID; each fails by throwing.
- **Policy instances** are built by the executor with `new`, their constructors taking no arguments, which the decorators' types require: workflow policies once per journey, before the dispatcher is created, where a failure is a refusal; step policies for every attempt, where a failure aborts with `policy could not be built`. They are not frozen: `Object.freeze` is shallow and does not reach private fields, so it cannot make an instance read-only, and it would turn a hook that changes its policy into `hook failed`. So chapter 6, 6.1 point 7 falls to its last sentence: rebuilding the instances is what keeps any change from outliving the attempt or the journey, as the last of Rust's notes for other languages says. The tech spec records it.
- **Roles** are interfaces. A workflow provides a role by implementing it, as `Orders implements Messages`. A policy names the roles it needs as its base class's type argument, `WorkflowPolicy<Messages>` or `StepPolicy<Messages & Payments>`, and a hook requests one with `@role<Messages>()`, which compiles only in a policy that names it. `@workflow` and `@withStep` compile only when the workflow class implements the roles of every policy they attach, so `role not provided` cannot be written. The builder keeps no list of roles: `.policy(Notify)`, and a step policy given to a step descriptor's builder, compile only when the workflow class implements every role the policy asks for, inferred from its base class's type argument, as with the decorators. A hook's role is the workflow's own value: a role request gets the workflow object. Nothing about roles exists at run time: if a cast slips a workflow past the types, the hook's call on the missing method throws, and the journey ends with `hook failed`.

### 8. Workflow declarations

- **`@workflow` makes the workflow descriptor** when its class is defined, and the builder's `build()` makes a new one for a workflow put together through it, before the constructor runs; either throws `Violations`, listing every violation of chapter 3, 3.6 at once: all fifteen except `mode not accepted`, which does not arise with one executor accepting both kinds, and `role not provided`, which does not compile. The workflow descriptor is an object of its own, never the workflow object: it holds references to the workflow class's input adapters, service providers and ID generator, whether its decorators marked them or they were named to the builder, and calls each with the workflow object as `this` (section 5, decision 12).
- **Each step states everything**: a retry budget (0 unless set, a non-negative integer checked when declared), whether abnormal terminations are retried (yes, unless `@withStep` sets `noRetryOnAbnormalTermination: true`, as Rust's attribute of that name, or the step descriptor's builder says so), its policies in order, and its rescue step.
- **`@workflow`'s `reporters`**, and the reporters given to the builder, list reporter classes, each built with `new`, with no arguments, for every journey, before the instance's own reporters.
- **Names** are non-empty strings, checked when declared, with branded types (`StepName`, `PolicyName` and so on) so that a plain string is not mistaken for one. A step named in an adapter's or a provider's `steps` is checked against the workflow's steps when the class is defined, or when `build()` runs for a workflow put together through the builder, since one decorator cannot see another's names at compile time.
- **`Orders.listing()`**, a static method of `Workflow`, gives each step's name, position, policies, input adapter, services with the provider serving each, and its rescue section, for what the decorators declared. The builder's own `.listing()` gives the same for what it has put together so far; both read a workflow descriptor, and neither needs a workflow object (section 5).
- **Input adapters** are methods of the workflow class marked `@inputAdapter`, or named to the builder with their tokens by position, their parameters marked with, or given tokens for, what they request (the step's name, the key, data from the workflow, the journey ID, read access to the data bag), returning `this.supply(value)` or `this.fromDataBag()`, as chapter 4, 4.11 point 1 suggests. Their access to the data bag has no method that writes, in its type or at run time, and shows nothing once their call has returned.
- **Service providers** are methods of the workflow class marked `@provider`, or named to the builder with their tokens by position, with a service token, a scope, the steps they serve, an optional key and name, and their parameters marked with, or given tokens for, what they request: the journey ID, `@journeyId()`, a value of the workflow, `@fromWorkflow(...)`, and a means of emitting `journey_*` events and setting global metadata, `@providerReporter()` (chapter 4, 4.9 point 7), and, for a provider of attempt scope, the step's name and the attempt, `@stepName()` and `@attempt()`. Unlike an adapter, a provider requests no key and no data bag. `@attempt()` or `@stepName()` on a provider of journey scope is the violation `attempt request in journey scope`, found with the other violations. A provider returns `this.provide(instance)` or `this.provide(instance, data)`, typed `Provided<T>` for the token's service, so returning nothing does not compile; whatever comes back otherwise through a cast is `service_provider_failed` and `step could not be built`. The implementation `service_provided` names is the instance's constructor name, or the service token's name for an object with no class of its own, as chapter 4, 4.9 point 6.3 allows; the tech spec warns that minifiers rename classes. `wrong service type` compares service tokens.

### 9. The workflow instance

- **`Orders.build(...).instance(initialData, { reporters, reportersGlobalMetadata })`**, `instance` being a method of `Workflow`, and likewise on `Orders.builder().constructWith(...).build()`, creates an instance: its initial data, then its journey ID, from the workflow's ID generator or `crypto.randomUUID()`, then its reporters, as chapter 5, 5.1 orders them. `reporters` lists reporters, or functions that take the journey ID and return one, so a reporter may receive the journey ID; they come after the reporters the workflow descriptor lists. It compiles only on a workflow object that the static `build()` or the builder's `build()` made, typed `Built<Orders>`, and throws, before any journey, saying to use `Orders.build()`, on one that a cast got past the compiler, so the executor never runs a workflow object without its checked descriptor (section 5).
- **The executor relies on one type,** `WorkflowInstance`, the counterpart of Rust's trait, which only `instance()` makes (section 5, point 7). It holds the workflow descriptor and the workflow object side by side, as Rust's `descriptor()` and `workflow()`, then the initial data, the journey ID, the reporters and the initial global metadata: `descriptor`, `workflow`, `initialData`, `journeyId`, `takeReporters()` and `takeGlobalMetadata()`. `instance()` takes the descriptor `#init` stored on the workflow object (section 5, decision 12).
- **An instance runs once.** Running it again is refused.

### 10. The executor and the engine

- **`LocalExecutor`**, with an optional dispatcher factory. `await executor.run(instance)` resolves to the journey's result; a refusal, before any journey, rejects with a `Refusal` error naming what refused it and carrying the error that caused it (decision 6).
- **Before the journey**, in this order: reject with a `TypeError` an instance that `instance()` did not make; refuse an instance that ran, or a call while a journey runs; refuse initial data or initial global metadata that is not a value, or that sets `journey_id`; build the workflow policies; create the dispatcher and add the guarded reporters; set `journey_id`, then the initial global metadata. A failure in any of the others is a refusal, with no event.
- **One journey at a time.** A call to `run` while the executor's journey is still running is refused before anything starts; parallelism comes from several executors.
- **One engine**, private, written once with `async` and `await`. It reads `instance.descriptor` and passes `instance.workflow` to every call the descriptor makes into the workflow, never calling a method of the workflow object itself (decision 12). It awaits whatever custom code returns, so synchronous and asynchronous steps, hooks, providers and reporters are all accepted. It never sets timers, never cancels and never yields on its own, so it runs on any event loop.
- **Inside the engine**, the same seams as Rust: the scan, a pure decision function, the step and hook callers, request resolution, services with journey-scoped instances kept until the journey ends, the rescue, the emitter with its replaceable clock, guards around reporters, and a runner seam that builds and runs a step, which scripted runs replace.
- **Hooks and reporters are called through one wrapper.** While the journey runs, every call the engine makes into a hook, which covers a role operation the hook calls, and every call into a reporter or the dispatcher, the guards around reporters included, goes through one wrapper. The call site gives the wrapper the rule chapter 5, 5.10 gives it: the abort reason, `hook failed` or `reporter failed`, or, while `journey_aborted` is delivered, that a failure is ignored (chapter 2, 2.3 point 4). Under the rule that a failure is ignored, the wrapper drops the failure and returns, so delivery goes on to the remaining reporters. Otherwise, when the call throws, or its promise rejects, or it returns after an abort was recorded during it, as when a dispatcher swallows the failure of a guarded reporter (chapter 2, 2.3 point 1) or a hook catches the journey-abort error and returns, the wrapper records the abort at once with that reason, unless an abort is already recorded, since the first abort reason stands, and throws instead the journey-abort error, of the class the package never exports, carrying the abort reason and, when the call threw, the thrown error, which the abort carries as chapter 5, 5.10 point 4 says. It is the class of the executor's signal (section 6), not a second one. A journey-abort error coming out of the call passes through the wrapper unchanged, so a hook ended at an emit on which a reporter failed aborts with `reporter failed`, not `hook failed`. The engine catches the error only where it runs the journey: it delivers `journey_aborted` and makes the recorded abort the journey's result, so nothing escapes `run`.
- **Other calls into custom code keep their own rule.** Before the journey there is no journey to abort: a failure of the dispatcher factory, of the dispatcher while the reporters are added, of a reporter or the dispatcher while the initial global metadata is set, or of a workflow policy while it is built, is a refusal (above). A step's constructor, a rescue step's included, an input adapter or a service provider that fails emits its failure event, if it has one, and aborts the journey with `step could not be built`, and a step policy that fails while it is built aborts it with `policy could not be built`, each carrying the error. A running step that throws anything but the journey-abort error terminates abnormally, unless an abort was recorded during the attempt, and its descriptor may retry it; a step that catches the journey-abort error and throws something else still ends the journey aborted, as section 6 says. Wherever the engine catches what custom code throws, a journey-abort error passes through unchanged, so a provider ended at an emit on which a reporter failed aborts with `reporter failed`.

### 11. Events, reporters and dispatchers

- **`Event` is a discriminated union on `kind`**, the snake_case names of chapter 2, one member per kind, each carrying its fixed fields: the sequence number from 1, the timestamp as an ISO 8601 string in UTC, the journey ID, the workflow name, and the fields of its kind. Events are deeply frozen, data included, so one reporter cannot change what the next one reads. No engine event has a field that can hold a data bag value.
- **Reporters** have `report(event)` and, optionally, `receiveGlobalMetadata(key, value)`, chapter 2, 2.1's **report** and **receive global metadata**, each returning nothing or a promise; the dispatcher's operation is `setGlobalMetadata`, as 2.2 names it. A `DebugReporter` prints each event, as Rust's does.
- **Dispatchers and their factories** follow chapter 2, 2.2; `DefaultDispatcher` calls reporters in the order added. The executor wraps each reporter it adds in a guard, so the rules of 2.3 hold whatever the dispatcher.
- **Global metadata** is set on the dispatcher before `journey_started` (the journey ID, then the instance's entries), and by steps, hooks and providers through their reporters while the journey runs. Setting `journey_id` while the journey runs aborts it with `reserved metadata key`, and the entry reaches no reporter.

### 12. The result and errors

- **`JourneyResult`**: the journey ID and a status that is a discriminated union: succeeded with the data bag, failed with the failure and the data bag, aborted with the abort and no data bag. `isSucceeded()`, `isFailed()`, `isAborted()`, `failure` and `abort` read it without a switch, as chapter 5, 5.14 suggests.
- **A failure** carries its cause, its reason and its error as chapter 5, 5.8 lists; **an abort** its reason, details and error. The result holds the thrown value itself, and its message: `error.message` for an `Error`, `String(value)` otherwise. Both can throw (a `message` getter that throws, or an object with no prototype), so the message is read defensively, with a fixed text when reading it fails, since nothing may escape `run`.
- **`Violations`**, **`Refusal`** and the test mistakes are `Error` subclasses.

### 13. Test support (`itinera/testing`)

The five parts of chapter 8, with its suggested names in camelCase: `RecordingReporter` with `events`, `globalMetadata` and `path`; `fakeProvider`, applied to an instance by a function of `itinera/testing`, so that nothing of test support is reachable without importing it; `scripted()` with `step`, `andStep`, `onAttempt`, `onEveryAttempt`, `onRemainingAttempts`, `willContribute`, `willEmit` (with optional data), `willSetGlobalMetadata`, `willSucceed`, `willFail`, `willSkip`, `willTerminateAbnormally`, `willRunForReal`, `ensureAllScripted`, `run`, and the record's `attempts`, `attempt` and `input`; the `Ending` a scripted attempt plays; and the recorders `Contributions`, `StepEventReporter`, `HookEventReporter` and a data bag built with `with`. A mistake in a test throws a `TestMistake` naming each problem, before the journey: a mistake in writing the script where it is written (chapter 8, 8.5 point 8), and what the script leaves out when it runs. `fakeProvider` takes the provider's name and a service token, so a fake making another service is the mistake `another service`, and a script that contributes, emits or sets global metadata for a step that declares no contributor or reporter is `no contributor` or `no reporter`.

**One harness with the conformance runner** (decision 11). The runner's scripted parts are test support's own mocks, so the conformance cases exercise the very mocks applications test with:

1. **A step mock** stands for a scripted step: a step configured with what it contributes, what it emits, the global metadata it sets, the outcome it returns, whether it throws, and so on, which ends each attempt through the `Ending` and is put into a workflow with the builder. It goes beyond chapter 8's five parts, as chapter 8 allows: it is the test tool that writes real steps to which chapter 8, 8.5 point 10 makes the `Ending` available.
2. **The recording reporter** stands for the runner's recording reporters, keeping exactly what chapter 8 says, so only the latest value of each entry of global metadata (chapter 8, 8.2).
3. **Three more mocks** go in `itinera/testing` beside chapter 8's five parts, as the step mock does, since the runner's scenarios need them and chapter 8 defines none of them: a policy mock, which gets exactly the hooks a scenario lists and records what they received; a reporter that fails; and a reporter that keeps every entry of global metadata in order, with the event received before each, which the runner's sentence "the reporter received the global metadata" reads. The policy mock is a class extending its base class, and each reporter a class implementing `Reporter`, as the builder requires of policies and reporters.
4. **Each mock lands in the stage whose runner first needs it**: the recording reporter in stage 2, the step mock and its `Ending` in stage 3, and the policy mock and the two reporters with the first scenarios that need them, each growing with what later stages' scenarios need. Until 0108 is listed, they are exported only from `itinera/unstable`, as the agents' manual requires for the API of a proposal not yet listed.
5. **Stage 10** moves them to `itinera/testing`, adds what test support still lacks, such as fake providers, scripted runs and the recorders, and claims `testing`. Scripted runs may use the builder.

## Rules made impossible, and rules enforced at run time

The specification lets a language make nine rules impossible to express, and itinera-rs excludes all nine with proofs. TypeScript is what itinera-ts supports, so five of them do not compile, each with a proof: a type test of `@ts-expect-error` lines, which fails the type check if the code ever compiles. Each proof lands with its feature, with its entry under `impossible` in `conformance.json`, as in Rust:

| Tag | What does not compile |
|---|---|
| `invalid-lifecycle` | a hook returning a lifecycle its kind may not return, such as a failure hook finishing the workflow |
| `rescue-skip` | a rescue step that skips: `RescueStep` has no `skip`, and its `run` must return a rescue outcome |
| `no-instance` | a provider returning anything but `this.provide(...)` |
| `role-not-provided` | a policy attached to a workflow class that does not implement the roles it names |
| `bag-write` | a write through an adapter's access to the data bag, which has no method that writes |

Where `any` or a cast can still slip past a type, the engine keeps its check, so that nothing escapes `run`: the lifecycle check, the `rescue skipped` abort and the provider check, each covered by unit tests. A cast around a role ends as `hook failed` (section 7).

The builder is a way to declare too, so its types keep the same five rules impossible, and each proof covers the builder as well as the decorators, since an excluded rule cannot occur in the language (chapter 3, 3.8 point 3). It does so with what refuses them for decorated classes: it takes steps, rescue steps and policies only as classes extending itinera's base classes (section 5), so a hook's lifecycle, a rescue step's outcome and a provider's `this.provide(...)` are typed by the same base classes and helpers, the methods it is given for hooks, adapters and providers are typed by their kind as the decorators type them, an adapter's access to the data bag is the same type with no method that writes, and `.policy(...)`, like a step policy given to a step descriptor's builder, compiles only when the workflow class implements every role the policy asks for (section 7).

The other four cannot be refused by types, so their scenarios run like the others, or do not arise:

| Tag | How itinera-ts enforces it |
|---|---|
| `journey-scope-request` | the violation `attempt request in journey scope`, found when the class is defined, since a parameter decorator cannot see its method's decorator (section 8) |
| `non-value` | the value check at every entry point, since types cannot refuse `NaN`, cycles or getters (section 2) |
| `late-handle` | handles closed when their attempt, hook or call ends |
| `mode-not-accepted` | does not arise: its two scenarios are also tagged `@capability-sync`, and `sync` is not claimed |

Five more tags, of test support, are enforced at run time: `undeclared-handles` by the mistakes `no contributor` and `no reporter`, `fake-service-type` by the mistake `another service` (section 13), and `attempt-zero`, `attempt-negative` and `attempt-fraction` by the mistake `no such attempt`.

One rule of chapter 3, 3.8 has no tag and cannot be enforced in TypeScript: a step keeping a service after its attempt. Chapter 4, 4.9 point 8.1 allows that, since the executor never lends the service again; the documentation says not to keep one.

## Testing

### 14. The conformance runner

- **`packages/conformance`**, run with `npm run conformance`, on cucumber-js (13.x), whose JSON formatter writes the Cucumber JSON report. It reads `ITINERA_CONFORMANCE_CASES`, `ITINERA_CONFORMANCE_TAGS` and `ITINERA_CONFORMANCE_REPORT`, and fails when a selected scenario fails or uses an undefined sentence. It is compiled with `tsc` before it runs, as `itinera` is, since the fixtures need `emitDecoratorMetadata`, which neither Node's type stripping nor esbuild emits.
- **Only the public API**, as in Rust: Given sentences fill a plain scenario model, and "When the workflow runs" turns it into descriptors and builds the scenario's workflow with the builder (section 5, decision 11), from a class extending `Workflow` that declares nothing, as itinera-rs's runner uses its builder, and names it with `.name(...)`. The runner records no metadata and runs no decorator; its workflow class has the methods it names to the builder as input adapters, providers and ID generator. How a step mock or a policy mock receives its scenario's script, for example through a mock class made per scenario, is settled in the tech spec of 0108 (see "Points to watch"). Its scripted parts are test support's mocks (section 13): each scripted step is a step mock, configured with what the scenario says each attempt does, each scripted policy is a policy mock, getting exactly the hooks the scenario lists and recording what they received, a reporter that fails is test support's, and the recording reporter, the reporter that keeps every entry of global metadata and a recording dispatcher factory record the rest. So a scenario's workflow goes through the same checks as an application's, `build()` refusing one put together wrongly, and conformance and test support are one harness. Step statuses are derived from the events.
- **The `run-conformance` action** of itinera-dev/actions runs it unchanged: it only needs a command.
- **Fixtures**, the counterpart of Rust's `@macros` features, live in `packages/conformance/features/fixtures`: workflows written by hand as an application writes them, declared with the decorators, driven through the cases' own sentences, with a Given sentence naming each workflow, such as `Given the payment workflow`.
- **Scenarios of a rule made impossible** are excluded through `conformance.json`, as in Rust.

### 15. TypeScript's own tests

- **Unit tests** with Vitest, in each package's `tests/unit`, mirroring `src`, and integration tests in `tests/integration`, named after the flows they check, together with the tests of the package as a whole, and shared fixtures in `tests/fixtures`, so the build compiles `src` alone; all named as sentences, with `it.each` named cases for one rule over several inputs.
- **Type tests** with Vitest's type checking (`expectTypeOf` and `@ts-expect-error`): every refusal at compile time of section 5, run on the oldest TypeScript applications may use, 5.5 (decision 14), and on the pinned one. TypeScript 5.0.4, the minimum before decision 14, was confirmed in stage 0 to type parameter decorators by their position, as 6.0 and 7.0 do: a mismatch at any position is refused with error TS1239. Stage 1's first layer added the CI job, `npm run typecheck-oldest`, which type-checks the sources, the tests and the examples on 5.5, fetched with `npx`. The proofs of the rules made impossible live in `packages/itinera/tests/integration/proofs.test-d.ts`, one named test each, which `conformance.json` points to.
- **Property-based tests** with fast-check, as Rust's proptest ones: first and last events, increasing sequence numbers, one outcome fact per attempt, one decision per failed attempt, attempt counts within the budget, no data bag values in engine events.
- **Examples in the documentation are real files** under `examples/`, compiled and run by the tests and pulled into the API reference with TypeDoc's `@includeCode`, so no example can rot.
- **The package itself** is checked with `publint` and `@arethetypeswrong/cli`, so its exports and types resolve for every consumer, `itinera/schema` included.

### 16. Continuous integration

Each job runs one npm script, as the organisation's automation rule requires: format, lint, type check, tests on Linux on Node 22 and 24, the LTS lines, and on the current Node 26, and on the newest LTS on Windows and macOS, build and package checks, the API reference with warnings as errors, a licence and advisory check of dependencies, type tests on TypeScript 5.5, the oldest applications may use, added by stage 1's first layer (decision 14), the tests of the actions under `.github/actions` (section "Release" for the release actions), conformance through `run-conformance`, the book through `check-book` (stage 12), `pr-has-issue`, `no-cross-repo-closing` and `commit messages`.

## Code rules for the agents' manual

The new AGENTS.md carries Rust's rules over where they are not about Rust:

- Names use the specification's vocabulary, in camelCase as proposal 0111 shows (`keepDefault`, `fromDataBag`, `isFirst`), and types in PascalCase.
- Types hold every constraint they can: branded names, an `Attempt` type counted from 1 with `isFirst`, discriminated unions for closed sets, `readonly` everywhere. A comment stating a constraint the type could enforce means the type is wrong.
- `tsconfig` turns on `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess` and `noImplicitOverride`; lint uses typescript-eslint's strict type-checked rules, with `no-floating-promises` and `no-explicit-any` as errors.
- No throw escapes `run` while a journey runs; declarations may throw before a journey, with a message saying what was wrong.
- Modules follow concepts; a file past 200 lines holds one thing; tests live in `tests`, beside `src`, with unit tests mirroring `src`.
- Enums that carry data, such as `Event` and `Outcome`, are discriminated unions, matched with `ts-pattern`'s `match(...).exhaustive()`; a plain `switch` over one passes typescript-eslint's `switch-exhaustiveness-check`. Closed sets of names, such as hook kinds and statuses, are declared with itinera's `closedSet`, which gives their names, parsing and every value from one declaration (decision 10).
- Array methods over loops that build a result, and chains that read as a sentence of named functions, as Rust's closure rule says.
- Reuse before writing: the standard library and the web platform, then packages already depended on, then well-known packages; write it ourselves only when none fits. Every runtime dependency has a stated reason in the tech spec that adds it.
- As few comments as possible, never referring to specification sections, issues or pull requests; no `TODO`.
- Every exported item documented in British spelling, with an example that compiles and runs.
- Decorators are the main way an application declares: a class extending one of itinera's base classes, marked with legacy decorators; a decorator gives way to another form only where section 4 says the language makes it impossible. The public builder puts a workflow together without decorators, from steps and policies as classes extending the same base classes, reporters as classes implementing `Reporter`, and methods of the workflow class, never loose functions, a class without decorators giving its tokens by position, and `build()` makes the workflow object an application runs (decision 11).
- Whatever TypeScript can refuse does not compile, and a type test shows it; a rule that types cannot hold is checked at run time.

## Decisions

Each was put to the maintainer one at a time, with a recommendation, before any code.

1. **Execution modes.** DECIDED (the maintainer, 2026-10-15): option 1.
   1. One asynchronous executor that accepts synchronous and asynchronous steps, hooks, providers and reporters alike; claim `async` and `testing`. *(Recommended: TypeScript is asynchronous by nature, a synchronous-only executor would refuse almost every real step, and a synchronous executor can be added later without changing this one.)*
   2. Both executors, `sync` and `async`, from one engine written as generators that a synchronous or an asynchronous driver runs; every part declares its mode, and `run` reports `mode not accepted`.
2. **How workflows are declared.** DECIDED (the maintainer, 2026-10-15 and 2026-10-16): decorators are the public API applications write, as close to Rust's macros as possible, giving way only where the language makes them impossible, and their whole surface is part of this plan (section 4). TypeScript, not JavaScript, is supported, so whatever TypeScript can refuse does not compile. Applications extend abstract base classes, which implement the interfaces the executor uses (section 5). There is no builder: the conformance runner declares classes too. A step receives its inputs as its constructor's parameters, each marked with its request. Decision 11 adds a public builder under the decorators, and decision 12 moves the interfaces the executor uses off the base classes, onto descriptor objects of their own.
3. **How requests name their types.** DECIDED (the maintainer, 2026-10-16), CHANGED (the maintainer, 2026-10-19): one path. Every request's type is a Standard Schema validator, optionally wrapped in `optional(...)`, and the engine checks every request one way, through the Standard Schema interface (section 3). The metadata supplies the type where it is unambiguous, and it becomes the matching built-in schema; elsewhere a request writes one of itinera's tokens, or any other Standard Schema validator, such as a Valibot or ArkType schema. The tokens keep their names, the vocabulary of the conformance cases, and their subpath, `itinera/value`, and are themselves Standard Schema validators built on Zod, reused rather than written: `integer` is `z.int()`, a safe integer, `listOf` and `objectOf` likewise, `guard(name, isT)` a Zod custom schema carrying its name, and `classOf(C)` a Zod schema carrying the class, so that the engine gives the step `C.fromValue(value)`. itinera writes no type checking of its own beyond that. `optional(schema)` takes any Standard Schema validator, since optional is the engine's concern: absence gives `None` before any check runs, and only a present value is checked. It is not itself a validator but a marker the engine reads, from `itinera/value`, accepted only as a request's own type or a typed read's, never inside `listOf` or `objectOf`, where a Zod `.optional()` field is written instead. `zod` 4 becomes a runtime dependency, re-exported as `z` from a new subpath, `itinera/schema`, so an application needs no install of its own, and the documentation recommends importing it from there, so that the application uses the same copy. Unchanged: a schema only checks, and the step receives the stored value, never the schema's output; a schema whose check is asynchronous is refused (CHANGED in stage 4, for the maintainer to confirm: when it first checks a value, not when its class is defined, since a Standard Schema validator shows that its check is asynchronous only when it runs, see "Points to watch"); the compiler checks the parameter against the schema's input type; and what follows when a check or a `fromValue` throws, left open then, waiting on [spec#113](https://github.com/itinera-dev/spec/issues/113), is now what proposal 0113 says (section 3). Zod 4's declarations need TypeScript 5.4, and Zod documents 5.5, so applications need TypeScript 5.5 (decision 14). On 2026-10-16 the tokens were run-time descriptions of itinera's own, with a Standard Schema validator as an optional second path; that is dropped. Generating every type from the declarations waits for after tier 1, since TypeScript 7 runs no compiler plugins.
4. **Package.** DECIDED (the maintainer, 2026-10-16): one package, `itinera`, with one subpath per concept mirroring Rust's modules, and test support at `itinera/testing`. On 2026-10-19 the maintainer confirmed that test support stays in this package, as the subpath `itinera/testing`, not a package of its own.
5. **What a value is.** DECIDED (the maintainer, 2026-10-16): plain JSON data, or an instance of a class that serialises itself with `toValue` and `fromValue`, turned into plain data when captured (section 2).
6. **A refusal from `run`.** DECIDED (the maintainer, 2026-10-16): `run` rejects with a `Refusal` error.

7. **Which decorators.** DECIDED (the maintainer, 2026-10-16): option 2. Many applications compile with `experimentalDecorators` and `emitDecoratorMetadata`, and a project compiles one kind of decorator or the other.
   1. One API that works under both kinds, with requests listed on the method's decorator.
   2. Legacy decorators only, with parameter decorators. Chosen. Each parameter decorator is typed against its parameter, so a mismatch does not compile (section 5). `emitDecoratorMetadata` is required, and supplies the type of a request that writes none (decision 3).
   3. Both: option 1, plus parameter decorators under the legacy kind only. Kept for when someone asks.

8. **Option and Result.** DECIDED (the maintainer, 2026-10-16), CHANGED (the maintainer, 2026-10-17): `Option` yes, from `ts-results-es` (Rust's names, no dependencies, CommonJS and ESM), re-exported from `itinera/option`: optional requests and data bag reads give an `Option`, and it is the only one of the two that applications meet. `Result` is used only inside itinera, where it makes sense, such as between the engine's own modules, and is never exported, nor met in anything an application writes or receives. Throwing is how custom code fails: a step's `run` returns an outcome or a promise of one, a rescue step's one of its two outcomes or a promise of it, an input adapter its supplied value or "from the data bag", and a provider its provided service, each or a promise of it, a hook its lifecycle, or nothing for a workflow hook, and the ID generator its journey ID, synchronously, since `instance()` is; each reports something abnormal by throwing, never by returning an error. On 2026-10-16 custom code could also return an `Err`, failing exactly as a throw does; that is dropped, and with it the recognition of an `Err` through its own methods. Since the subpath would re-export only `Option`, `Some` and `None`, it is named `itinera/option`, no longer `itinera/result`. It re-exports the values `Some` and `None` as well as the type, and the documentation and a lint rule say to import them only from there: the review found that an ESM application importing them from `ts-results-es` directly fails to type-check against itinera's CommonJS declarations.

9. **How a value is checked and copied.** DECIDED (the maintainer, 2026-10-16): option 1. CHANGED (the maintainer, 2026-10-19): option 2, unless an npm package does all of it; none does (point 3).
   1. `is-json-value`, which reports each problem with its path, bundled into the CommonJS build since it is ESM only, with `structuredClone` for the copy and one rule of itinera's refusing objects whose prototype is not plain, such as a `Date`. *(Recommended: reuse, with a dozen lines of glue.)*
   2. A walk of itinera's own.
   3. Why it changed: building option 1 in stage 1's first layer showed three things its dozen lines of glue cannot do. `toValue()` must be called at any depth, since `classOf(C)` reads a class back inside `listOf` and `objectOf` (section 3), so a walk of itinera's own is needed anyway, and its prototype rule is a second walk. `is-json-value` and `structuredClone` each read every getter, so a getter is read twice, and what the check saw may not be what is stored. And `is-json-value` is ESM only: Node 22.12 can `require` it, but Jest's CommonJS loader cannot, so it would have to be bundled into the build, which today is `tsc` alone. One walk does it all in about 190 lines, with no dependency: it calls `toValue()` wherever an object has one, refuses what is not plain data, a cycle, a symbol key, a property that is not enumerable or a list with an empty slot, builds the copy as it goes, and says where the first problem is. It lives in `src/value/capture.ts`, so changing it again changes that file alone. No npm package does all of it: `is-json-value` and `safe-json-value` resolve `toJSON` and let a `Date` through, cloners such as `rfdc`, `klona` and `copy-anything` refuse nothing, and serialisers such as `superjson` make text or tagged JSON.

10. **Enums.** DECIDED (the maintainer, 2026-10-16): `ts-pattern` for exhaustive matching, the typescript-eslint rule for `switch`, and `enum-plus` for the names, parsing and every value of closed sets, as Rust's derives give them. CHANGED (the maintainer, 2026-10-19): closed sets are declared with `closedSet`, a dozen lines of itinera's own in `src/closed-set.ts`, in place of `enum-plus`. `enum-plus` ships declarations that do not type-check without `skipLibCheck` on TypeScript 6.0, in each version tried, 3.0.0, 3.1.8, 3.2.1 and 3.3.1, and itinera's build and the check on its oldest TypeScript compile every declaration an application compiles. `closedSet` makes a frozen object of names, each mapped to the specification's text, with every value in order and a check that reads a value back only when written exactly, and the type of the same name is the union of its values. The closest package, `ts-enum-util` 4.1.0, checks cleanly and reads the values of a frozen object and checks a text against them, through `$enum(StepHook).getValues()` and `$enum(StepHook).isValue(text)`, but that replaces only `Object.values` and a lookup in a `Set`, the couple of lines the agents' manual writes rather than depends on. Zod's `z.enum`, a dependency from stage 4, keeps its names under `.enum`, where each cannot carry its own documentation. TypeScript's own string `enum` does not take a string literal, so `"step_failed"` would neither compare with it nor narrow `Event`. The tech spec of 0011 says more.

11. **A builder.** DECIDED (the maintainer, 2026-10-16): a public builder under the decorators (section 5).
    1. `Workflow` gets a static `build(...args)` and a static `builder()`, in which `this` is the derived class. `Orders.build("corner")` takes the workflow descriptor that `@workflow` assembled from the decorators of `Orders` and checked when the class was defined (decision 12), then calls the `Orders` constructor with arguments the compiler checks against that constructor; `Workflow.build()` does not compile, since the base class is abstract. `build()` is how an application makes the workflow object it runs. Verified on TypeScript 6.0.3 and 7.0.2.
    2. `build(...args)` passes the application's own arguments straight to `new this(...args)`, the base class's constructor taking nothing and doing nothing, then calls the base class's ECMAScript private method `#init(descriptor)`, which no application code can call or override and which a derived class's own `init` does not clash with. `#init` stores the checked workflow descriptor on the object and marks it as runnable (decision 12). `build()` returns it typed `Built<Orders>`, through a `unique symbol` only itinera can name, and `instance()` takes `this: Built<this>`, so `new Orders("corner").instance(order)` does not compile; if a cast gets past the compiler, `instance()` checks the mark and throws, saying to use `Orders.build()`. Verified: TypeScript 6.0.3 compiles and runs it, and 7.0.2 type-checks it.
    3. The builder collects lists of descriptors, the parts of a workflow descriptor: step descriptors, workflow policies, reporters, input adapters, service providers and the ID generator. A step descriptor has a builder of its own, as itinera-rs's has, started by the step class's static `builder(name)`. CHANGED (the maintainer, 2026-10-19): a builder per step, in place of the one options object shared with `@withStep` that stage 3 settled. Decorated classes fill these lists when they are defined, and `build()` reads them. Whoever adds to the lists makes a new descriptor, which the builder checks whole before the constructor runs.
    4. A class given to the builder without decorators writes its requests' tokens by position, each typed against its parameter, so a token that does not match does not compile (point 9). Verified.
    5. It is public: applications that do not use decorators, including those built with esbuild, Vite or tsx, declare their workflows with it. Decorators remain the main way and still need `emitDecoratorMetadata`; decision 7 is unchanged for them.
    6. The conformance runner builds its scripted workflows with the builder, records no metadata and runs no decorator; its workflow class has the methods it names to the builder as input adapters, providers and ID generator, and how a step mock or a policy mock receives its scenario's script, for example through a mock class made per scenario, is settled in the tech spec of 0108. Its scripted parts are test support's mocks: a scripted step is a step mock, a scripted policy a policy mock, and a reporter that fails or keeps every entry of global metadata is a reporter mock (point 12), so conformance and test support are one harness. Each mock lands in the stage whose runner first needs it, exported only from `itinera/unstable` until 0108 is listed, and stage 10 moves them to `itinera/testing` (section 13). The fixtures drive hand-written decorated workflows, as itinera-rs's runner uses its builder and its `@macros` features use the macros.
    7. **`constructWith`.** DECIDED (the maintainer, 2026-10-16): the builder's `constructWith(...args)` takes the derived class's constructor arguments, typed `ConstructorParameters<C>` so the compiler checks them against the constructor, and holds them until `build()`, as in `Orders.builder().constructWith("corner").build()`. The builder's `build()` takes no arguments: it checks the whole descriptor and throws `Violations`, then calls `new Orders(...args)`, then the base class's `#init(descriptor)`. For a class whose constructor needs arguments, `build()` does not compile until `constructWith` was called, since the builder's type carries a ready state; a class whose constructor takes none may call `build()` straight away. The static `Orders.build("corner")` stays, as the short form of `Orders.builder().constructWith("corner").build()` for a workflow that adds nothing through the builder. It differs from Rust, where the workflow's struct is initialised before its builder is asked for, because here the descriptor is checked before the object exists and `#init` runs after it is made. Verified: TypeScript 6.0.3 runs it, and 7.0.2 type-checks it.
    8. **Naming.** DECIDED (the maintainer, 2026-10-16): the builder has `.name("orders")`, and a name given there replaces the one `@workflow` gave, since the builder makes a new descriptor. The builder's `build()` throws, saying the workflow has no name, when neither `@workflow` nor the builder named it.
    9. **Classes and methods only.** DECIDED (the maintainer, 2026-10-16): every step, rescue step and policy given to the builder is a class extending its base class, `Step`, `RescueStep`, `StepPolicy` or `WorkflowPolicy`; a reporter is a class implementing `Reporter`, as in `@workflow`'s `reporters`; an input adapter, a service provider or the ID generator is a method of the workflow class, which extends `Workflow`; never a loose function. Each base class has an ECMAScript private `#` field, so only a real subclass fits, and anything else does not compile. A class without decorators gives its tokens by position: `needs`, one per constructor parameter, and `run`, one per parameter of `run`, each typed against its parameter. For example, `Orders.builder().step(Charge.builder("charge").needs(input("amount", integer)).run(service("payments", PAYMENTS))).constructWith("corner").build();` compiles only for a `Charge` extending `Step` whose constructor takes a number and whose `run` takes what `PAYMENTS` names (CHANGED in stage 4, for the maintainer to confirm: each token by position is the request decorator itself, since a type alone cannot say which request a parameter makes, see "Points to watch"). A policy, an adapter or a provider gives its tokens likewise, per hook or method. The base classes' protected helpers, such as `this.succeed()`, `this.supply(value)` and `this.provide(service)`, make outcomes, lifecycles, supplied values and provided services exactly as for decorated classes. A decorated class may be given too, its decorators giving the tokens. The same base classes and helpers that keep the five rules made impossible from compiling for decorated classes keep them from compiling for the builder's parts. Verified for steps on TypeScript 6.0.3 and 7.0.2.
    10. **Roles.** DECIDED (the maintainer, 2026-10-16): the builder keeps no list of roles. `.policy(Notify)` compiles only when the workflow class implements every role the policy asks for, inferred from the policy's type argument, `WorkflowPolicy<Roles>` or `StepPolicy<Roles>`, as with the decorators, and a role request gets the workflow object. Verified on TypeScript 6.0.3 and 7.0.2.
    11. **Listing.** DECIDED (the maintainer, 2026-10-16): the static `Orders.listing()` lists what the decorators declared, and the builder has its own `.listing()` for what it has put together so far. Both read a workflow descriptor, so they list alike, and neither needs a workflow object.
    12. **Mocks beyond chapter 8.** DECIDED (the maintainer, 2026-10-16): a policy mock, a reporter that fails, and a reporter that keeps every entry of global metadata in order, with the event received before each, go in `itinera/testing` beside chapter 8's five parts, as the step mock does, and in `itinera/unstable` until 0108 is listed. The recording reporter stays exactly as chapter 8 says (section 13).

12. **The workflow descriptor is its own object.** DECIDED (the maintainer, 2026-10-16): option 1.
    1. Base classes stay for everything an application calls, and the engine's methods move to a `WorkflowDescriptor` object of its own, never on a class's public surface. *(Chosen.)*
       1. `WorkflowDescriptor<W>` is an object separate from the application's workflow object, as in itinera-rs, where `WorkflowInstance` gives the executor `descriptor()`, the `WorkflowDescriptor<W>` the macros generate, and `workflow()`, the application's `W`, side by side.
       2. Decorators generate no code. Each marking decorator records what it marks, such as a step class with its options or a reference to a method such as `Orders.prototype.pricing`, in itinera's registry, keyed by the class. `@workflow`, running last, reads it, checks it for violations and builds the `WorkflowDescriptor` object once, when the class is defined; the builder's `build()` builds a new one. The descriptor holds references to the marked methods, or to the methods named to the builder, and calls them with the workflow object as `this`, so `this.shop` and `this.supply(...)` work in them.
       3. `#init(descriptor)` stores the descriptor on the workflow object, and `instance()` puts the descriptor and the workflow object side by side in the `WorkflowInstance`. The static `build()` calls `#init` directly; the builder, a separate class, calls it through a function that `Workflow.builder()`, inside `Workflow`, hands the builder's constructor, whose class is exported as a type only, so applications cannot call it, and `Workflow` has no public `attach`. `instance()` reads `this.#descriptor` and returns a public `WorkflowInstance`, whose `descriptor` the executor reads without touching the private field. Verified on TypeScript 6.0.3. The engine reads `instance.descriptor` and passes `instance.workflow` to the descriptor's calls.
       4. `Workflow` no longer implements `WorkflowDescriptor`. An application class shows only the static `build()`, `builder()` and `listing()`, `instance()`, and the protected helpers `supply`, `fromDataBag` and `provide`. It inherits none of the engine's methods, so nothing can be overridden by accident, since TypeScript has no `final`, and the name the interface's `provide` shared with the helper `provide` no longer clashes.
       5. `WorkflowDescriptor`'s methods take the workflow object as their first argument where they call into it, as Rust's do. The members, whose signatures the tech spec of 0062 settles: `name`, `steps()`, `policies()`, `reporters()`, `adapt(workflow, step, key, access)`, `provide(workflow, step, service, key, access)`, `generateJourneyId(workflow, data)` and `listing()`. `WorkflowInstance`: `descriptor`, `workflow`, `initialData`, `journeyId`, `takeReporters()` and `takeGlobalMetadata()`.
       6. Hand-written descriptors implement the same public interfaces and are checked by `run`, as before. CHANGED (the maintainer, 2026-10-19): descriptors and instances are sealed, and none is written by hand (decision 15).
       7. The premise holds: the application marks the class that represents the workflow, and nothing it writes changes.
       8. Decorators could add methods to a class at run time, but TypeScript never changes a class's type because of a decorator, so injecting the API an application calls is not an option. The plan relies on no such method: what applications call comes typed from the base classes, the helpers `this.succeed()`, `this.fail(reason)`, `this.keepDefault()`, `this.supply(value)` and `this.provide(service)`, the static `build()`, `builder()` and `listing()`, and `instance()`, typed from the derived class's constructor, and the roles through `WorkflowPolicy<Roles>`; what the engine calls lives on the descriptor.
    2. Drop the base classes, and have applications import free functions in place of the helpers. Considered and rejected: applications would import a function for each helper, and the roles a policy names, which ride on its base class's type argument, would need another mechanism.

13. **How a failure of custom code aborts a journey.** DECIDED (the maintainer, 2026-10-17): one wrapper in the engine makes every call into a hook, a role operation the hook calls, a reporter or a dispatcher while the journey runs, taking from its call site the abort reason, or that a failure is ignored while `journey_aborted` is delivered (section 10). What the wrapper throws, the journey-abort error, is also the executor's signal: one class, which the package never exports, caught only where the engine runs the journey (section 6). Anything a running step throws is an abnormal termination, unless an abort was recorded during the attempt, which then stands.

14. **The oldest TypeScript applications may use.** DEFAULT (2026-10-19, the maintainer may override): TypeScript 5.5, in place of the 5.0 that stage 0 set. Zod 4's declarations, which itinera re-exports from `itinera/schema` (decision 3), use `NoInfer`, so they need TypeScript 5.4 or later, and Zod documents 5.5 as its minimum; on an older TypeScript an application would compile them only with `skipLibCheck`. It was taken as a default, since the maintainer asked for the work to go ahead with defaults. Section 4 ("Compilers"), section 15 and the Tooling section follow it, and stage 1's first layer adds the CI job that runs the type tests on 5.5.

15. **Sealed descriptors and instances.** DECIDED (the maintainer, 2026-10-19): option 1. `WorkflowDescriptor`, `StepDescriptor` and `WorkflowInstance` are sealed, as the base classes are: each is a class with ECMAScript private `#` fields and a private constructor, exported as a type only, so only the decorators, the builder and `instance()` make one. One written by hand does not compile where one is expected, and `run` rejects with a `TypeError` an instance that `instance()` did not make, which only a cast lets through, before any refusal. A rejection rather than a `Refusal`, since the specification's refusals do not include it and it is a misuse that types rule out, as a cast past `instance()` throws (a default, the maintainer may override). This replaces section 5, point 7 as stage 3 wrote it, where a hand-written descriptor ran and `run` checked it for every violation. No proposal to the specification is needed: chapter 5, 5.9 point 2 asks that any executor run any instance of the language, and though it names producing one by hand, it leaves how that abstraction is expressed to each language, and itinera-ts seals it, so every instance the language allows is one itinera made, which the executor runs; and since each descriptor is checked when it is made, frozen, and reached only through a frozen instance, chapter 3, 3.7 point 2 asks `run` to check none. `PolicyDescriptor` is sealed the same way when it lands. It also removes the gap of stage 3 about hand-written instances and descriptors that throw, since none is custom code any longer, and the names a hand-written descriptor would have needed to make.

Defaults taken without asking, which the maintainer may still change: the repository layout, Node 22 and later, the tooling of the Tooling section, Conventional Commits from the first commit, and the stage order.

## Points to watch

- **A gap in the specification stops the work**, as in Rust: it goes to the maintainer and to `spec`, never decided in TypeScript.
- **Unawaited emit calls** are the main TypeScript-only trap; section 6 says how the engine keeps the order and avoids unhandled rejections, and stage 5 tests both.
- **Implementation names** come from constructor names, which minifiers change; the documentation says so.
- **Typing the decorators** is the hardest TypeScript in the plan; stage 3 starts with the type tests of section 5, before the code they check.
- **Two copies of the package** in one application would not share the registry, tokens or error classes; the single CommonJS build behind the ESM layer prevents one source of them, two installed versions remain, and the documentation says to keep one copy. Likewise for Zod, whose `z` applications import from `itinera/schema` (section 3).
- **Zod's major version is part of itinera's API**, since `itinera/schema` re-exports it: moving to a new major of Zod changes what applications meet.
- **The cases move to `v0.1.0`** during this work; if anything changes after rc.16, the change is adopted as Rust adopts it.
- **Calling a workflow class's constructor directly.** `new Orders("corner")` still compiles, since a constructor cannot be made `protected` without losing the typing of the arguments of `build()` and `constructWith()`, but the object it makes cannot make an instance: `instance()` does not compile on it, and throws on it at run time behind a cast (section 5).
- **What decisions 11 and 12 leave to the tech spec of 0062**: the exact signatures of the members of `WorkflowDescriptor` and `WorkflowInstance`, which decision 12 sketches, and of the builder's methods. Stage 3 settled those it needs, as defaults the maintainer may change, in [0062](specs/0062-workflow-descriptors.md): the builder names a method of the workflow class by its name, a step descriptor's builder was one options object shared with `@withStep`, which the maintainer changed on 2026-10-19 to a builder per step, started by `Charge.builder("charge")`, as itinera-rs has, and a builder method refuses a misuse at once, from the method, rather than at `build()` with the violations. Stage 4 settled the rest, as defaults the maintainer may change, in the tech specs of [0062](specs/0062-workflow-descriptors.md) and [0010](specs/0010-hooks-lifecycles-and-roles.md): what a builder is given by position for each parameter is the request decorator itself, such as `input("amount", integer)` or `contributor()`, with its type written, since a bare type, as `needs(integer)`, cannot say which request a parameter makes nor its key; a class whose decorators declare its requests cannot be given them by position too; a policy declared without decorators has a builder of its own, `Audit.builder(name?)`, naming each hook's method with its requests, and one declared with `@stepPolicy` or `@workflowPolicy` is given as the class itself; a rescue step likewise, `Refund.builder()`; input adapters and service providers are named to the workflow builder with their options and requests; and `adapt(...)` and `provide(...)` join the workflow descriptor in stages 5 and 8, when adapters and providers run. Stage 5 settled `adapt(workflow, step, answers)`, given what the engine resolved the adapter's requests to, in [0062](specs/0062-workflow-descriptors.md).
- **What stage 3 settled for the executor**, as defaults the maintainer may change, in the tech specs of [0012](specs/0012-local-executor.md), [0009](specs/0009-running-a-workflow.md) and [0083](specs/0083-what-failures-carry.md): `LocalExecutor` takes its dispatcher factory as its one optional constructor argument; an instance handed to `run` counts as run even when it was refused, so a second `run` of it is refused with `instance ran`; `Refusal` carries the error of the custom code that caused it as its standard `cause`, beside `error` and `errorMessage` on `refused`; and the fixed text for a message that cannot be read is `an error whose message could not be read`. The executor's decision after an abnormal termination, planned for stage 6, landed in stage 3, since nothing may escape `run` once steps run; the same pure function decides after a failure since stage 5, which lets steps fail, and a skip needs no decision. For reporters, the wrapper of section 10 is the guards together with the journey's `emit`, which turns a failure into the abort; stage 7 adds hooks to it.
- **How a mock receives its script**: settled in stage 3, as a default the maintainer may change, in the tech spec of [0108](specs/0108-test-support.md): through a class made per scripted step, closing over its script (section 14).
- **Value conversions that fail, a gap in chapter 5, 5.10.** The table of calls into custom code did not list the conversions of a value: `toValue()` when a value is captured, and `fromValue`, a guard or a Standard Schema validator when a request, or an input adapter's typed read of the data bag, reads a value. The proposal [spec#113](https://github.com/itinera-dev/spec/issues/113) asked for them to be covered: a conversion that fails while a value is read, by throwing, returning an error, or a guard or schema refusing, means `wrong type`, and one that throws while a value is captured means `not a value`, or `step could not be built` for an input adapter's supply, and initial data whose conversion fails is refused by `run` as not a value. The specification accepted it as proposal 0113, which lets an abort or a refusal carry the conversion's error; itinera's carry none. Stage 1 implemented it for `toValue()` at capture, and stage 5 for reads, in `src/value/read.ts`, and the cases `v0.1.0-rc.16` check it, with the capability `value-conversions` claimed. Its tech spec is [0113](specs/0113-value-conversions.md) (sections 2 and 3).
- **A schema whose check is asynchronous**, found in stage 4: section 3 planned to refuse it when its class is defined, but a Standard Schema validator says nothing of its check until it runs, when it returns a promise rather than a result. Stage 4 records the schema as given. DECIDED in stage 5, for the maintainer to confirm: a check that returns a promise is a check that failed, so the read ends as spec#113 says a refused one does, `wrong type` for a request and `other type` for a typed read of the data bag, carrying no error. The promise is never awaited, and its rejection is caught and dropped, so it is never an unhandled rejection. The tech spec of [0056](specs/0056-data-bag-values.md) records it.
- **What a typed read with `optional` gives**, found in stage 5: section 3 lets a typed read of the data bag take a schema wrapped in `optional`, but does not say what it gives for a key with no value. DECIDED in stage 5, for the maintainer to confirm: such a read is typed `Read<Option<T>>` and never reads absent, but present, holding `None` for a key with no value and `Some` of a value of the type, as an optional input reaches a step. The other choice is `Absent` for the missing key, so that only a value reads present. The tech spec of [0091](specs/0091-adapters-read-the-data-bag.md) records it.
- **Two input adapters with one name**, found in stage 4: chapter 3, 3.4.1 says an adapter's name is unique within its workflow, but chapter 3.6 lists no violation for two adapters sharing one, and does not say what one adapter naming a step twice is. DECIDED (the maintainer, 2026-10-19): the violation `duplicate adapter name` is added, and a step named twice in one adapter's or provider's list is `step adapted twice` or `service provided twice`, as [spec#116](https://github.com/itinera-dev/spec/issues/116) proposed. The specification accepted it as proposal 0116, whose tech spec is [0116](specs/0116-duplicate-adapter-names.md), and the cases `v0.1.0-rc.16` check it.
- **Zod's declarations name the global `URL`**, found in stage 4, so an application compiling them with neither Node's types nor the DOM library, and without `skipLibCheck`, gets an error from them. itinera's own build and its check on the oldest TypeScript compile with Node's types, which give `URL` and match the Node versions itinera supports, rather than the DOM library, which would let itinera's code use browser globals that Node lacks; the documentation says so.

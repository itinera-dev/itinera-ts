# 0062: Workflow descriptors, and executors independent of how workflows are written

Tech spec for [proposal 0062](https://github.com/itinera-dev/spec/blob/main/proposals/0062-workflow-descriptors.md), implemented in [#23](https://github.com/itinera-dev/itinera-ts/issues/23). The [tier 1 plan](../tier-1-plan.md) holds what crosses proposals: section 4 the decorators, section 5 the registration, the builder and the descriptors, and decisions 11 and 12. [0008](0008-steps.md) holds the steps and [0061](0061-instance-carries-journey-id-and-reporters.md) the instance.

Status: complete, and 62 is listed in `conformance.json`. Stage 3 added the base class `Workflow`, the descriptor interfaces, the registry, `@workflow`, `@withStep` and `@idGenerator`, the metadata check, the first violation, the static `build()` and the builder with `name`, `step`, `reporter`, `idGenerator`, `constructWith` and `build`. Stage 4 added the type tokens, the request decorators, every other base class and declaring decorator, every other list, the tokens by position, every violation and the listing, and listed the proposal. Its first layer has added the type tokens and `itinera/schema`, the table of requests, and the requests of steps; its second, the policies attached by `@withStep` and `@workflow` (see [0010](0010-hooks-lifecycles-and-roles.md)); its third, rescue steps attached by `@withStep`, the input adapters and service providers of a workflow class (see [0003](0003-rescue-steps.md), [0060](0060-input-adapters-attached-to-steps.md) and [0095](0095-services-provided-to-steps.md)), and the guard on `strictNullChecks`; its fourth, a builder per step, `Charge.builder(name)`, given to the workflow builder's `step`; its fifth, the sealed descriptors and instances; its sixth, the requests given to a builder by position, the policy descriptors, a builder for each kind of policy and for a rescue step, and the workflow builder's policies, input adapters and service providers; its seventh, every violation and the listing.

## API

0062 is listed, but what it defines names the steps, policies, input adapters and providers of proposals not listed yet, such as 0008 and 0010, so everything here stays exported only from `itinera/unstable` until they are, as the agents' manual requires. The base class is defined in `src/workflow/base.ts`, re-exported by `src/workflow.ts`, which becomes the subpath `itinera/workflow` then, with its submodules in `src/workflow/`.

### The descriptors, the executor's contract

- **Sealed.** `WorkflowDescriptor`, `StepDescriptor` and `WorkflowInstance` are classes with ECMAScript private `#` fields and private constructors, exported as types only, as the plan's decision 15 says. Each class's static block hands its module the one function that makes one, so only `assemble`, `describeStep` and `instanceOf` make them, and an object or a class written by hand with the same members does not compile where one is expected. `run` rejects with a `TypeError` an instance that `instance()` did not make, told apart by its private field, which only a cast lets through, before it refuses anything. Each is frozen once made, but for an instance's reporters and global metadata, which it hands over once.
- **`WorkflowDescriptor`**, in `src/workflow/descriptor.ts`, is an object of its own, never the workflow object, as decision 12 says. Its members, as this proposal defines them:
  - `name`, the `WorkflowName`;
  - `steps()`, the step descriptors in the order they run, the same frozen array on every call;
  - `reporters()`, a new reporter of each listed class for every call, which `instance()` calls when it creates an instance, so that each instance has reporters of its own;
  - `generateJourneyId(workflow, initialData)`, which calls the method `@idGenerator` marked with the workflow object as `this`, or makes a random UUID v4 with `crypto.randomUUID()` when there is none. Since stage 5, the method may take one parameter, marked `@dataBag()`, the only request an ID generator may make, as chapter 5, 5.2 point 2 lets it derive the ID from the instance's data, and as itinera-rs gives its ID generator `&DataBag`. It is given a data bag holding the initial data, captured as `run` captures it, without the values that are not values, which `run` then refuses, and emptied once the method returns, as an input adapter's is, in `src/workflow/id-generator.ts`. The initial data is captured again by `run`, as it must be whatever the ID generator did, so a value that converts itself with `toValue()` converts twice, and an ID generator reads what the conversion gave when the instance was made. A returned value that is not a string throws a `TypeError`, since a cast can slip one past the types.
- **`StepDescriptor`**, in `src/step/descriptor.ts`: `name`, `retryBudget`, `retryOnAbnormalTermination` and `build(needs)`, which makes a new step for each attempt, giving its constructor `needs`, the values the engine resolved its requests to. It keeps the rescue step attached to the step and the step's requests in a private field, which `rescueOf` and `requestsOfDescribed` read, and gives its step policies with `policies()`, as `PolicyDescriptor`s (see [0010](0010-hooks-lifecycles-and-roles.md)).
- `WorkflowDescriptor.policies()` gives the workflow policies. `WorkflowDescriptor.adapt(workflow, step, answers)` calls the input adapter attached to the step on the workflow object, with `answers`, what the engine resolved the adapter's requests to, in the order it declares them, and gives what the method returns; it throws a `TypeError` for a step no adapter is attached to. Its arguments differ from the `adapt(workflow, step, key, access)` decision 12 sketched, because an adapter's requests are any of `@stepName()`, `@key()`, `@fromWorkflow`, `@journeyId()` and `@dataBag()` in any order, and resolving `@fromWorkflow` may abort the journey, which only the engine can do (see [0060](0060-input-adapters-attached-to-steps.md)). `provide(...)` joins it in stage 8 ([0095](0095-services-provided-to-steps.md)), and stage 5 gave `generateJourneyId` the initial data ([0061](0061-instance-carries-journey-id-and-reporters.md)).
- **`WorkflowDescriptor.listing()`**, in `src/workflow/listing.ts`, lists the steps in order without running anything, as chapter 3, 3.1 point 2 says: a `ListedStep` per step with `step`, its name, `position`, a `Position` counted from 1, a number branded so that only itinera makes one, `policies`, the names of its step policies in the order they were attached, `adapter`, the name of its input adapter, left out when it has none, as events leave out what they do not carry, `services`, a `ListedService` per service its `run` requests, in order, with its `key` and the name of the `provider` that serves it, and `rescue`, its `ListedRescue`, left out for a step without a rescue step, with the rescue step's `step`, `adapter` and `services` but no position or policies. The provider serving a step is the one of its key attached to it, or else the one of its key attached to no step, which admission made sure exists. The names follow itinera-rs's `ListedStep`, `ListedRescue` and `ListedService`.
- **`Orders.listing()`**, a static method of `Workflow`, lists what the decorators of `Orders` declared through the descriptor `@workflow` made, and throws for a class without `@workflow`, as `build()` does. The builder's own `listing()` lists what it has put together so far, through the descriptor `build()` would make, so it throws `Violations`, or an error when the workflow has no name, as `build()` does. Neither makes a workflow object, as section 5 of the plan, point 6, says.

### How declarations become descriptors

- **The registry**, in `src/workflow/registry.ts`, keeps a `Declaration` per workflow class in a `WeakMap`: its name, its step descriptors, its reporter classes, its workflow policies, as policy descriptors, its input adapters and its service providers, in the order their methods are written, its ID generator and, once `@workflow` made it, its descriptor. `declarationOn(class)` gives a class's declaration to every decorator that adds to it, and throws for a class that does not extend `Workflow` itself. It is never exported, and nothing is added to the class.
- **`@withStep(Step, options)`** checks that the step class was declared with `@step`, makes its step descriptor at once, which checks its name and retry budget, and puts it first in the list. Class decorators run from the bottom up, so putting each first leaves the list in written order, and `@workflow` has nothing to reorder.
- **`@idGenerator()`** records the method it marks, a reference to `Orders.prototype.orderId`, with its name, which `@workflow` reads to accept a method carrying requests that `@idGenerator` marks, and its requests. Its decorator is generic in the method's type, as the plan's note 1 says, and is typed as the interface `IdGeneratorDecorator`, so that its type parameter has documentation.
- **`@workflow({ name, reporters, policies })`**, on the top line, runs last. It records the name, the reporter classes and the workflow policy classes, refuses a method that carries requests but is marked with neither `@inputAdapter` nor `@provider`, then makes the descriptor with `assemble`, which checks every violation it knows and throws `Violations`, and keeps it in the registry. The name is required: a class without `@workflow` is named by the builder's `name()`, and the builder's `build()` throws when neither named it.
- **Checked when the class is defined**, throwing an `Error` that says what is wrong: a name that is empty, a retry budget that is not a whole number from 0, a class that does not extend `Workflow` itself, `@workflow` twice on one class, `@withStep` written above `@workflow`, a step class not declared with `@step`, `@idGenerator` on what is not a method, two ID generators, and a parameter of the ID generator with no request, or with a request other than `@dataBag()`, which a parameter typed `unknown` lets through.
- **The metadata check**, in `src/declaration.ts`, which imports `reflect-metadata`: a method decorator throws when the compiler recorded no `design:paramtypes` for its method, naming the compiler option `emitDecoratorMetadata`. Parameters are counted from those types, or from the function's `length` where none were recorded, as for a `run` with no decorated parameter. Until stage 4 adds the request decorators, any parameter is a parameter with no request.

### Requests and their types

- **The type tokens**, in `src/value/token.ts`, re-exported by `src/value.ts`, are Zod schemas, so each is a Standard Schema validator: `string` (`z.string()`), `integer` (`z.int()`, a safe integer), `number` (`z.number()`, which accepts only finite numbers), `boolean`, `list` (a list of any values) and `object` (a record of any values, never a list or `null`); `listOf(item)` and `objectOf(shape)`, `z.array` and `z.object` of the Zod schemas they are given, `objectOf` letting other properties through unchecked; `classOf(C)`, a `z.custom` whose check accepts any value and which carries `C` in a `WeakMap` that the engine reads from stage 5, typed for the compiler as an instance of `C`, since that is what a request receives; and `guard(name, isT)`, a `z.custom` of the type guard, described by its name. `ValueClass<T>` is a class with a static `fromValue(value)`.
- **`optional(schema)`** takes any Standard Schema validator and returns a frozen marker, `Optional<S>`, that holds the schema under a symbol only itinera holds, so only `optional` makes one; `unwrapped(type)` gives the schema a request's type checks and whether it is optional. It is not a schema, so it does not compile inside `listOf` or `objectOf`, whose items must be Zod schemas.
- **`RequestType`** is what a request may name: `StandardSchemaV1 | Optional<StandardSchemaV1>`. `Answer<T>` is what such a request gives its parameter: the schema's input type, as Standard Schema infers it, or an `Option` of it for an optional one.
- **A schema whose check is asynchronous** cannot be refused when its class is defined, as section 3 of the plan says, since a Standard Schema validator shows that its check is asynchronous only by returning a promise when it runs. Stage 5 refuses it when it reads a value, as the tech spec of the read will say.
- **The table of requests**, in `src/declaration.ts`, keeps, in a `WeakMap` keyed by the class, a map from the method, or `undefined` for the constructor, to the request at each position, in the internal union `Request` of `src/declaration/request.ts`. Every request decorator is made by `marking` or `markingValue`, in `src/declaration/marking.ts`, which records what its function makes of the parameter, and refuses a second request on one parameter. `requestsOf(class, key)` reads the requests in the order of the parameters, counted from the metadata or the function's `length`, and throws naming the first parameter that carries none, which replaces stage 3's refusal of every parameter.
- **A request that writes no type** reads it from the metadata as its decorator runs, in `src/declaration/metadata.ts`: `Number`, `String` and `Boolean` become the tokens `number`, `string` and `boolean`, a class with a static `fromValue` becomes `classOf` of it, and anything else, such as the `Object` the compiler records for an interface or a union, throws, saying the request must write its type. With no metadata at all, it throws naming `emitDecoratorMetadata`.
- **Typed by position.** Each decorator's type is an interface whose one call signature takes the target, the method's key and the parameter's literal position, as the plan's note 6 says: `RequestDecorator<A, P>` for a request that gives an `A`, and `ValueRequestDecorator<T, P>` for a request for a value of type `T`, or of the parameter's own type when `T` is `undefined`. `P` is a union of `Place`s, each a target and the keys a request may be made on: `Place<StepClass, undefined>` for a step's constructor, `Place<Step, "run">` for its `run`. `ParameterOf<T, K, I>` finds the parameter's declared type, and a parameter that does not accept what the request gives makes the position's type a string literal saying so, as the plan's note 8 suggests, such as `"the parameter's type does not accept what the request gives"`. With no type written, `ReadFromMetadata<P>` accepts only exactly `number`, `string` or `boolean`, or a class that serialises itself. These types live in `src/declaration/parameter.ts` and are re-exported by `src/workflow.ts`.
- **The requests of steps**, recorded by `@step` for its constructor and its `run` (see [0008](0008-steps.md)): `@input(key, type?)` on the constructor, and `@service(key, serviceType)`, `@contributor()` and `@stepReporter()` on `run`. The requests of hooks are in [0010](0010-hooks-lifecycles-and-roles.md), those of rescue steps in [0003](0003-rescue-steps.md), of input adapters in [0060](0060-input-adapters-attached-to-steps.md) and [0091](0091-adapters-read-the-data-bag.md), and of providers in [0095](0095-services-provided-to-steps.md). A method decorator that takes only some kinds of request, such as `@inputAdapter`, reads its requests through `requestsMadeBy(prototype, key, allowed, what)`, which throws, when the class is defined, naming the first request of a kind not allowed, such as `Orders.price: an input adapter cannot request @attempt`.
- **Without `strictNullChecks`** `null` belongs to every type, so a request decorator could not refuse a parameter whose type does not accept what it gives. `Strict<I>`, in `src/declaration/parameter.ts`, is `I` when the option is on, and otherwise the string literal `"itinera needs the compiler option strictNullChecks"`, so the position's type of every request decorator makes none compile without it, as section 4 of the plan, point 3, asks.

### Violations

`Violations`, in `src/workflow/violation.ts`, is an `Error` holding every violation found, at least one, with one line of its message per violation, such as `duplicate step name: charge`. Each `Violation` is a member of a discriminated union on `kind`, whose values are the closed set `ViolationKind`, written as chapter 3, 3.6 names them. `violationsOf` checks a workflow's steps, policies, input adapters and providers, and `assemble` throws `Violations` with every one it finds, so `@workflow` throws when the class is defined and the builder's `build()` before the constructor runs.

- **Thirteen kinds.** Chapter 3, 3.6 names fourteen, and the maintainer accepted a fifteenth, `duplicate adapter name`, ahead of the proposal to the specification that adds it ([spec#116](https://github.com/itinera-dev/spec/issues/116)). `role not provided` does not compile, since a policy names its roles in its base class's type argument (see [0010](0010-hooks-lifecycles-and-roles.md)), and `mode not accepted` does not arise, since the local executor accepts both execution modes, so neither has a kind, as the plan's section on rules made impossible says.
- **What each names**, in the submodules of `src/workflow/violation/`, each with its own interface:
  - `hook defined twice`, `steps.ts` and `hooks.ts`: `StepHookDefinedTwice`, the step, the hook and every policy defining it, in order, or `WorkflowHookDefinedTwice`, the hook and the workflow policies;
  - `duplicate step name` and `rescued step retried`, `steps.ts`: the step's name, once per name, in the order found, a rescue step's name, `<step name>_rescue`, counting among the names;
  - `duplicate adapter name`, `input adapter for unknown step` and `step adapted twice`, `adapters.ts`: the repeated name; the adapter and the name it was attached to; or the step and every adapter attached to it, once for each time it is attached;
  - `service not provided`, `service requested twice` and `wrong service type`, `services.ts`: the step, or rescue step, and the key, with the provider serving another type;
  - `service provided twice`, `duplicate provider name` and `service provider for unknown step`, `providers.ts`: the key and the step, or none for providers attached to no step, with every provider; the repeated name; or the provider and the name it was attached to;
  - `attempt request in journey scope`, `scope.ts`: the provider of journey scope requesting the attempt or the step's name.
- **Order.** Violations come in the order itinera-rs finds them: duplicate step names, rescued steps retried, hooks defined twice for each step, then for the workflow, duplicate adapter names, input adapters for unknown steps, steps adapted twice, services requested twice, then not provided or of the wrong type, duplicate provider names, providers for unknown steps, services provided twice, and attempt requests in journey scope. Within a kind they follow the order of the steps and of the declarations, where itinera-rs sorts some of them by name.
- **Which provider serves a step**, in `src/service/serving.ts`, which the listing reads too: the one of the key attached to the step, or else the one of the key attached to no step.

### The base class and `build()`

- **`Workflow`** is abstract. Its constructor takes nothing and does nothing. It keeps its descriptor in the ECMAScript private field `#descriptor`, set only by the private method `#init(descriptor)`.
- **`Orders.build(...args)`**, typed `this: C` with `C extends new (...args: never[]) => Workflow`, takes the descriptor `@workflow` made, calls `new this(...args)`, checked as `ConstructorParameters<C>`, then `#init`. It returns `Built<InstanceType<C>>`, the object marked by a `unique symbol` the module never exports. `Workflow.build()` does not compile, since `Workflow` is abstract, and a class without `@workflow` throws, saying it has no descriptor to build from.
- **`instance()`** takes `this: Built<this>`, so it does not compile on an object made with `new`, and throws, saying to use `build()`, when a cast gets one past the compiler. What it makes is in [0061](0061-instance-carries-journey-id-and-reporters.md).

### The builder

`WorkflowBuilder<C, Ready>`, in `src/workflow/builder.ts`, is exported as a type only, so an application gets one from `Orders.builder()`, a static method of `Workflow` typed `this: C` as `build()` is.

- **It starts from the class's declaration**: the name, the step descriptors, the reporter classes, the workflow policies, the input adapters, the service providers and the ID generator the decorators recorded, copied, so what it adds never changes the class's own descriptor. A class without decorators starts from nothing.
- **What it adds**, each method returning the builder: `name(name)`, in place of the name `@workflow` gave, checked not to be empty at once; `step(builder)`, a step descriptor made at once from a step's builder (see "A builder per step"); `policy(...)`, a workflow policy, a class declared with `@workflowPolicy` or a policy's builder (see [0010](0010-hooks-lifecycles-and-roles.md)); `inputAdapter(key, options, ...requests)` and `provider(key, serviceType, options, ...requests)`, a method of the class named as `@inputAdapter` and `@provider` mark one (see [0060](0060-input-adapters-attached-to-steps.md) and [0095](0095-services-provided-to-steps.md)); `reporter(Reporter)`, a reporter class; and `idGenerator(key, ...requests)`, the name of a method of the class, typed `IdGeneratorKey<InstanceType<C>>`, the keys of the methods that take nothing or the data bag and return a string, whose method it records, with `dataBag()` by position for a method that takes the data bag. A name keeps it safe from a minifier, which leaves property names alone, and lets the compiler check it against the class.
- **Classes, not decorators.** A step's builder starts from any class extending `Step`, declared with `@step` or not, and also one extending another step class, as test support's mocks made per scenario will (see [0108](0108-test-support.md)); only `@step` requires a class to extend `Step` itself. A step's parameters are checked as `@step` checks them, at once.
- **`constructWith(...args)`**, typed `ConstructorParameters<C>`, keeps the arguments and returns the builder typed `WorkflowBuilder<C, true>`.
- **`Ready`** is a phantom type parameter, `true` when `[] extends ConstructorParameters<C>`, so for a class whose constructor needs an argument `build()`, typed `this: WorkflowBuilder<C, true>`, does not compile until `constructWith` was called, while a class whose constructor needs none builds straight away.
- **`build()`** makes a new descriptor with `assemble`, which throws `Violations` or an error when the workflow has no name, before the constructor runs, then calls `new C(...args)` and gives the object its descriptor. It reaches `#init` through a function `Workflow.builder()` hands the builder's constructor, written inside `Workflow`, so only `Workflow`'s own code can write it; `WorkflowBuilder` is exported as a type only, so no application can make a builder with a function of its own. Every `build()` makes a new descriptor and a new object.
- **Only a class extending `Workflow` itself** has a builder, as only such a class may be declared: `builder()` on a class extending another workflow class throws, since what the parent declared would not carry over, and inheriting declarations can then come later without breaking anything.
- **The policies attached.** `StepOptions<P>` and `WorkflowOptions<P>` take `policies`, a list of policy classes typed `P`, empty unless given, whose policy descriptors `@withStep` and `@workflow` attach. The builders take a policy class or a policy's builder, one at a time, and a step's builder or the workflow builder's `policy` does not compile on a workflow that does not implement the roles the policy requests (see [0010](0010-hooks-lifecycles-and-roles.md)).
- **A builder per step.** `Charge.builder(name)`, a static method of `Step` typed `this: C`, `C extends StepClass`, so `Step.builder(...)` does not compile, starts a `StepBuilder`, in `src/step/builder.ts`, as itinera-rs's `StepDescriptor::new(name, factory)` starts a step descriptor: `Orders.builder().step(Charge.builder("charge").retryBudget(2).noRetryOnAbnormalTermination())`. The maintainer chose it on 2026-10-19, in place of the one options object shared with `@withStep` that stage 3 settled. It checks the name when it starts, and each method checks what it is given at once, the retry budget as `@withStep` does, and `needs` and `run` a parameter they leave without a request; when neither gave a class's requests, the workflow builder's `step` refuses a parameter its decorators left without one. The workflow builder's `step(builder)` makes the step descriptor from what the step's builder has so far, through a function only `StepBuilder`'s own code writes, so the step's builder exposes no way to make a descriptor. It also has `needs(...requests)` and `run(...requests)`, the step's requests by position, `policy(...)`, a step policy, and `rescue(...)`, a rescue step, a class declared with `@rescueStep` or a rescue step's builder (see [0003](0003-rescue-steps.md)). `StepClass` and `StepMockClass` name `builder`, so a class held as either has it.
- **Requests by position.** A class declared without decorators is given its requests by position: a step's `needs(...)` and `run(...)`, a rescue step's likewise, each hook of a policy's builder, and the workflow builder's `inputAdapter` and `provider`. What each is given is the request decorator itself, as `input("amount", integer)`, `service("payments", PAYMENTS)` or `contributor()` make it, a default of this layer: the plan's example, `needs(integer)`, gives only a type, which cannot say which request a parameter makes, the key of an input or of a service, or that it asks for a contributor. Each decorator's interface carries, in the types only, under a `unique symbol` of `src/declaration/token.ts`, a `Given<A, P, W>`: what the request gives, where it may be made, and whether its type is written. `Token<T, P>` accepts a decorator that gives what a parameter of type `T` accepts, may be made in the place `P`, and writes its type, and `Tokens<T, P>` asks one per parameter of the tuple `T`, none left out; `ParametersOf<T, K>` and `MethodKey<T, R>` find a method's parameters and the methods returning `R`. A request for a value whose type is not written, such as `input("amount")`, does not compile by position, since no metadata is read there. At run time `marking` and `markingValue`, in `src/declaration/marking.ts`, remember in a `WeakMap` the request each decorator stands for, and `requestsGiven` reads them in order, throwing at once for what is not such a decorator, a parameter left without one, and a class or method whose decorators declare its requests already, so that the two cannot disagree.
- **When it refuses.** A misuse of a builder method throws at once, from that method, as the decorators throw when the class is defined, so the error points at the line that is wrong: an empty name, a step's empty name or retry budget, from the step's builder, a step's parameter with no request, from its builder's `needs` or `run`, or from the workflow builder's `step` when neither gave the requests, an ID generator that is not a method of the class, a second ID generator, and what the requests by position, the policies' builders, the rescue step's builder, the input adapters and the service providers refuse, each in its own tech spec. These are misuses, not violations of chapter 3, 3.6, which `build()` still collects whole and throws together as `Violations`. The plan's table of checks put every check at `build()`; this is a default the maintainer may change.
- **Refused**: at compile time, `Workflow.builder()`, a step class not extending `Step`, a reporter class whose constructor takes arguments, the name of a method that takes a parameter or does not return a string, or of a field whose type is not such a method, requests by position that do not fit their parameters, are too few or too many, or write no type, a policy whose roles the workflow does not implement, an input adapter or a provider that is not a method returning what it must, arguments that do not match the constructor, and `build()` before `constructWith` when the constructor needs arguments; at once, the misuses above, a field holding a function named as ID generator, which the types cannot tell from a method, and a class extending another workflow class.

## Dependencies

- **`zod`** 4.6.7, re-exported as `z` from the subpath `itinera/schema`, `src/schema.ts`. It gives the type tokens their checks, their shapes and their Standard Schema interface, so itinera writes no type checking of its own, and it ships CommonJS and ESM builds with types for both, which the single CommonJS build needs. An ESM application importing `zod` itself loads its ESM build, a second copy beside the CommonJS one itinera loads, so the documentation says to import `z` from `itinera/schema`. Zod's declarations name the global `URL`, which an application compiles with Node's types or the DOM library, so the package's own build and its check on the oldest TypeScript compile with Node's types rather than with an empty list of types. Node's types give `URL` and match the Node versions itinera supports, where the DOM library would let itinera's own code use browser globals Node lacks.
- **`@standard-schema/spec`** 1.1.0, the Standard Schema interface's own types, which a request's type and `optional` are typed with. Zod defines the same interface, but does not export it from a path a CommonJS build can import, and the package has no code.
- **`reflect-metadata`** 0.2.2, a peer dependency that `src/declaration.ts` imports itself, so an application never has to import it first. It reads the parameter types the compiler records with `emitDecoratorMetadata`, which no part of the language or the platform reads. TypeScript's emitted code records them only when `Reflect.metadata` exists as the class is defined, which importing itinera's decorators guarantees.

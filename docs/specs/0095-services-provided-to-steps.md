# 0095: Services provided to steps

Tech spec for [proposal 0095](https://github.com/itinera-dev/spec/blob/main/proposals/0095-services-provided-to-steps.md), implemented in [#31](https://github.com/itinera-dev/itinera-ts/issues/31). The [tier 1 plan](../tier-1-plan.md) holds what crosses proposals, section 8 the service providers, [0008](0008-steps.md) the steps that request services, and [0062](0062-workflow-descriptors.md) the table of requests.

Status: complete, and 95 is listed in `conformance.json`. Stage 4 has added `serviceType` and `@service`, a step's request for a service, then `@provider`, what a provider returns and `@providerReporter`. Its sixth layer has added providers to the builder, its seventh has added the violations about services and the listing, and stage 8 runs the providers while a step is built, lends their instances to its `run`, gives the runner its service sentences and listed the proposal. Stage 9 listed [0003](0003-rescue-steps.md), so the scenarios that also name its rescue steps run.

## API

Since stage 10, its API is exported from the subpaths of its concepts, chiefly `itinera/service`. It is defined in `src/service.ts`, with its submodules in `src/service/`.

- **`ServiceType<T>`** is a token for a type of service, since an interface does not exist at run time. `serviceType<T>(name)` makes one: a frozen object holding its name, for people, typed through a `unique symbol` that only itinera can name, so only `serviceType` makes one. Two service types are the same only when they are the same object, which is how `wrong service type` will compare them. An empty name throws.
- **`@service(key, serviceType)`** marks a parameter of a step's `run` with a request for a service, always required. It compiles only on a parameter of `run` of a class extending `Step`, whose declared type accepts the token's service type. It records the key and the service type in the table of requests.

- **`@provider(serviceType, { perAttempt?, steps?, key?, name? })`** marks a method of a workflow class as a service provider of the service type given. It is of journey scope unless `perAttempt` is `true`; it serves the steps it names, at least one when `steps` is given, so an empty list does not compile, and `<step name>_rescue` for a rescue step (see [0098](0098-rescue-step-adapters-and-providers.md)), or, with no `steps`, every step that requests its key and has no provider of its own for it. Its key and its name are the method's unless given. It is typed as the interface `ProviderDecorator<T>`, generic in the method's type, and compiles only on a method of a class extending `Workflow` that returns a `Provided<T>` for the token's service, or a promise of one, so a provider returning nothing, a bare instance, or an instance of another service does not compile. It records the provider in the class's declaration, in the order the methods are written.
- **What a provider may request**: `@journeyId()`, `@fromWorkflow(key, type?)`, `@providerReporter()`, `@stepName()` and `@attempt()`. Any other request throws when the class is defined, naming the method and the request. `@stepName()` or `@attempt()` on a provider of journey scope is the violation `attempt request in journey scope`, found with the other violations when the workflow is built (see [0062](0062-workflow-descriptors.md)).
- **`Provided<T>`** holds the instance and, optionally, the data for reporters, and is typed through a `unique symbol` only itinera names, so only `this.provide(instance)` or `this.provide(instance, data)`, a protected helper of `Workflow`, makes one; `data` compiles only when it is a value. Each object it makes is recorded, in `src/service/provider/provided.ts`, so `isProvided` tells it from one a cast makes, which stage 8 turns into `service_provider_failed`.
- **`@providerReporter()`**, in `src/service/reporter.ts`, requests a `ProviderReporter`, whose `info`, `warning` and `error` emit `journey_info`, `journey_warning` and `journey_error`, and whose `setGlobalMetadata` sets global metadata, each returning a promise, as chapter 4, 4.9 point 7 asks.
- **On the builder**, `provider(key, serviceType, { perAttempt?, steps?, key?, name? }, ...requests)` names a method of the workflow class, typed `MethodKey<InstanceType<C>, Provided<T>>` for the service type's `T`, so a method providing another service, or a field, does not compile, with its requests by position (see [0062](0062-workflow-descriptors.md)). It throws at once as `@provider` throws when the class is defined, and for a field holding a function or a method that declares its requests with decorators.
- **Which provider serves a step**, in `src/service/serving.ts`: the provider of the key attached to the step, or rescue step, or else the one of the key attached to no step. Admission checks every service a step or rescue step requests against it, in `src/workflow/violation/services.ts` and `providers.ts`: `service not provided`, `service requested twice`, `wrong service type`, comparing the service types as objects, `service provided twice`, which includes one provider listing a step twice, `duplicate provider name` and `service provider for unknown step`. The listing shows each service a step requests with the name of the provider serving it.
- **`WorkflowDescriptor.provide(workflow, step, key, answers)`** calls the method of the provider serving the step under the key, with the workflow object as `this` and the answers in the order the provider declares its requests, and gives what it returns. It throws a `TypeError` when no provider serves the step under the key, which admission rules out. The provider's method is recorded with it, as an input adapter's is.
- **Resolving the services**, in `src/engine/services.ts`, happens while a step is built, after its inputs and before its constructor runs, so a step that cannot be built from its data never causes a provider to be called, in the order its `run` declares them. The engine then lends each instance to `run`, in place, beside the handles. A step's constructor cannot use its services, as chapter 4, 4.9 point 8.2 allows, since a service is requested only in `run` here: the plan's decorators put services on `run`, where a step uses them.
- **Scopes.** A provider of journey scope is called the first time an attempt of a step it serves requests its key; its instance is kept in `Journey.kept`, under the provider's name, and lent again to every later attempt it serves, with no event. Once the journey's result is made, however it ended, the engine clears the map, in `src/engine.ts`, which is how an instance is released, as chapter 4, 4.9 point 4.3 asks each language to record: itinera keeps no reference to it, even through a handle an application kept, and calls nothing on it. An instance of attempt scope is held only by the attempt's `run`.
- **Calling a provider**, in `src/engine/provider.ts`: its requests are answered in order, in `src/engine/provider/answer.ts`, the journey ID, data from the workflow, read as a hook's is and naming the provider in `optional_input_absent`, `required data missing` and `wrong type`, its own provider reporter, the step's name and the attempt. A request that aborts the journey stops there, and the provider is not called. The engine awaits the method and every call it made on its reporter, then closes the reporter, so a later call throws where it is made. If the journey was aborted meanwhile, such as by a reporter failing on the provider's event, the abort stands and nothing the provider returned is looked at. A throw or a rejection emits `service_provider_failed` and aborts the journey with `step could not be built`, naming the provider and carrying the error. A return that `this.provide(...)` did not make, which only a cast lets through, `undefined` included, emits nothing and aborts the journey with `unexpected result`, naming the step, the provider and the key (see [0122](0122-unexpected-results.md)). The "nothing at all" of chapter 4, 4.9 point 6.2 cannot be written, as the proof for `no-instance` shows.
- **The provider reporter** is made by the same handles as a step's and a hook's, in `src/engine/handles.ts`: its events, `journey_info`, `journey_warning` and `journey_error`, carry the provider, the step and the attempt as their source, and come before `service_provided`, in the order the provider made its calls.
- **Refused when the class is defined**: an empty name or key, a request a provider may not make, a parameter with no request, a missing compiler option `emitDecoratorMetadata`, and a class that does not extend `Workflow` itself. `@workflow` refuses a method that carries requests but is marked with neither `@provider` nor `@inputAdapter`.

## Tests

- `tests/unit/service/request.test.ts`: a service type is named as given, is a new object each time, even under the same name, cannot be changed, and refuses an empty name; and what `@service` records.
- `tests/unit/service/request.test-d.ts`: a service type is made only by `serviceType`, and `@service` does not compile on a parameter of another type, on the constructor, on a method other than `run`, or outside a step.
- `tests/unit/service/provider.test.ts`: each provider recorded in order with its service, scope, steps and requests, an empty name or key, what is not a method, and a request a provider may not make.
- `tests/unit/service/provider/provided.test.ts`: `isProvided` with what the helper makes and what a cast makes.
- `tests/unit/service/provider.test-d.ts`: a provider with its requests, one providing another service or a bare instance, one outside a workflow, an empty list of steps, data that is not a value, and `Provided` from a plain object.
- `tests/unit/service/reporter.test.ts`: what `@providerReporter()` records.
- `tests/unit/engine/services.test.ts`: an instance of journey scope made once and lent to every attempt and step it serves, never to another journey; one of attempt scope made for each attempt; a provider attached to a step preferred; services resolved in the order `run` declares them, after the inputs, and lent in place; no provider called for a step whose inputs abort, or that does not request its key.
- `tests/unit/engine/journey.test.ts`: every instance of journey scope let go of once the journey ends. `tests/unit/engine/handles/holder.test.ts`: a provider named in a late handle's message, in an abort and as having set global metadata.
- `tests/unit/engine/provider/answer.test.ts`: what a provider is given, in order, and `optional_input_absent` naming it.
- `tests/unit/engine/provider.test.ts`: not called when a request aborts; `service_provided`; a throw and a rejection as failures, and `undefined` and a bare object as unexpected results; its reporter's events and global metadata before `service_provided`; a reporter failing on its event; its reporter refused once its call returned.
- `tests/unit/workflow/descriptor.test.ts`: `provide` calling the provider serving a step, and refusing a step none serves.
- `tests/unit/workflow/builder.test.ts` and `tests/unit/workflow/builder.test-d.ts`: a provider named to the builder with its requests, one providing another service, and each refusal.
- `tests/unit/service/reporter.test-d.ts`: `@providerReporter` on a parameter of another type or in a hook.
- `tests/unit/workflow/base.test.ts`: what `this.provide(...)` makes, with and without data.
- `tests/unit/workflow/violation/services.test.ts`, `providers.test.ts` and `scope.test.ts`: each violation about services and providers. `tests/unit/workflow/listing.test.ts`: the services listed with the provider serving each.
- `examples/service.ts`: a step requesting a payment gateway. `examples/provider.ts`: providers of both scopes. `examples/descriptors.ts`: `provide`.
- `tests/integration/proofs.test-d.ts`: a provider returning nothing or a bare instance does not compile, with the decorator or with the builder, the proof of the `@no-instance` exclusion in `conformance.json`.
- `packages/conformance`: the runner's service sentences, its labellers and meters, and its providers, one method of the scenario's workflow class each, playing every scenario of 0095, 0102 and 0104 that runs.

# 0008: Steps

Tech spec for [proposal 0008](https://github.com/itinera-dev/spec/blob/main/proposals/0008-steps.md), implemented in [#4](https://github.com/itinera-dev/itinera-ts/issues/4). The [tier 1 plan](../tier-1-plan.md) holds what crosses proposals, section 6 the steps, and [0062](0062-workflow-descriptors.md) the descriptors.

Status: complete, and 8 is listed in `conformance.json`. Stage 3 added the base class `Step`, the outcome of success, `@step` and the step descriptor. Stage 4 added the requests of a step's constructor and `run`. Stage 5 resolves them, and adds the other outcomes, contributions and the handles; stage 7 called the hooks around the outcomes and listed the proposal.

## API

Since stage 10, its API is exported from the subpaths of its concepts, chiefly `itinera/step`. It is defined in `src/step.ts`, with its submodules in `src/step/`.

- **`Step`** is abstract. Its `run(...requests)` is abstract and public, as the plan's note 6 requires for parameter decorators to type its parameters, returning an `Outcome` or a promise of one, so a step without `run`, or whose `run` returns anything else, does not compile. An application compiling with `noImplicitOverride` writes `override run()`.
- **Only a subclass is a step.** `Step` has the ECMAScript private field `#step`, so a class that only has the same members does not have the type of a step, `StepClass`, which `@step` and `@withStep` take, and whose static `builder(name)` starts a step's builder for the workflow builder (see [0062](0062-workflow-descriptors.md)).
- **`Outcome`** is a discriminated union on `kind`, in `src/step/outcome.ts`: `Success` (`"success"`), `Fail` (`"failure"`, with its reason) and `Skip` (`"skipped"`, with its reason when it gives one), made only by the protected helpers of `Step`: `this.succeed()`, `this.fail(reason)`, `this.skip()` and `this.skipBecause(reason)`. The names `Fail` and `Skip` follow the helpers, since `Failure` and `Failed` already name what the result carries in `itinera/journey`. Each outcome is frozen, and the engine accepts only an outcome the helpers made, kept in a `WeakSet`, so anything else a cast lets `run` return aborts the journey with `unexpected result`, never retried (see [0122](0122-unexpected-results.md)).
- **Reasons.** A helper takes a `GivenReason`: a code alone, or `{ code, message?, details? }`, whose details are typed `T & AsValue<T>`, so an object that serialises itself is accepted and a `Date` is not. The details are captured when the helper is called, as chapter 4, 4.3 point 3 says, and the `Reason` the outcome carries holds the captured copy. Details that are not a value, which only a cast or `NaN` lets through, leave the reason without details and mark the outcome, and the engine aborts the journey with `not a value`, naming the step, once the attempt ends, with no outcome fact. The helper cannot abort the journey itself, since a step does not reach the journey, and throwing would be an abnormal termination.
- **`@step()`** records, in a `WeakMap` keyed by the class, which `@withStep` reads, what the class requests: the requests of its constructor's parameters, its needs, and those of `run`'s, in order, read from the table of requests (see [0062](0062-workflow-descriptors.md)). When the class is defined it throws if the class does not extend `Step` itself, if it keeps static data, if it is declared twice, or if a parameter of its constructor or of `run` has no request. `Step.builder(name)` reads the same requests from a class not declared with `@step`, until stage 4 lets it give tokens by position.
- **No static data.** A step is built for each attempt and keeps nothing between attempts or journeys, so a step class keeps no static data (plan, decision 16). `WithoutStaticData<C, B>`, in `src/declaration/static-data.ts` and exported from `itinera/step`, with the example `examples/static-data.ts`, is the class `C` with each public static property it adds to those of its base class `B`, its own or inherited, required to be a function: `@step()` and `Step.builder` take `this` or their target as `WithoutStaticData<C, typeof Step>`, so a class with a public static field does not compile, and the error names the property. Types cannot see a `protected` or `private` static, nor tell an accessor from a field, so `refuseStaticData(target, base, what)` checks at run time, from the class up to its base class, every static property but a function, an accessor included, other than the built-in `name`, `length` and `prototype`, and throws naming each one; `@step()` calls it when the class is defined, and `Step.builder` when it starts the builder. A module variable or an ECMAScript-private static field cannot be seen either way, so the documentation says not to write one.
- **The requests of a step.** `@input(key, type?)` marks a parameter of the constructor with an input, required unless its type is wrapped in `optional`, its type written as a token or any other Standard Schema validator, or read from the metadata. `@service(key, serviceType)`, from `itinera/service`, `@contributor()`, from `itinera/journey`, and `@stepReporter()` mark the parameters of `run`. Service types and `@service` are in [0095](0095-services-provided-to-steps.md). Each decorator compiles only in its place, the constructor or `run` of a class extending `Step`, and on a parameter whose declared type accepts what it gives. Stage 5 has resolved the inputs as a step is built: `build(needs)` gives the constructor what the engine resolved, in `src/engine/build.ts`, each input from the step's input adapter or the data bag (see [0060](0060-input-adapters-attached-to-steps.md)), read as [0056](0056-data-bag-values.md) says. A required input without a value aborts the journey with `required data missing`, a value of another type with `wrong type`, and an optional input without one is `None`, emitting `optional_input_absent`. A constructor that throws aborts it with `step could not be built`, and so does a constructor request only a rescue step may make, which a cast lets through. The requests of `run` are lent in order, in `src/engine/run.ts`: the attempt's contributor for `@contributor`, its step reporter for `@stepReporter`. Stage 8 lends each service its provider made, resolved while the step is built (see [0095](0095-services-provided-to-steps.md)); a `run` requesting anything else, which only a cast lets through, aborts the journey with `step could not be built`, saying which request it is.
- **The requests of a step hook about its step**, in `src/step/request.ts`, compile only in a step policy: `@stepName()`, giving a `StepName`, `@attempt()`, giving an `Attempt`, and `@failureReason(options?)` and `@error(options?)`, giving a `Reason` and what the attempt threw, `unknown`, or, with `{ optional: true }`, an `Option` of either, as chapter 6, 6.11 point 3 suggests. A rescue step's constructor requests the reason and the error too, from stage 4's next layer. The hooks themselves are in [0010](0010-hooks-lifecycles-and-roles.md).
- **`Contributor`** and **`StepReporter`** are interfaces, `contribute(key, value)`, and `info`, `warning` and `error`, each with a message and optional data, and `setGlobalMetadata(key, value)`, each returning a promise. Values are typed `T & AsValue<T>`, so an interface whose members are values is accepted and a `Date` is not. The handles that implement them for an attempt are made by `AttemptHandles`, in `src/engine/handles.ts`, as frozen objects of functions, so a step reaches nothing else of the engine through them.
- **Contributions.** A contribution is captured when it is made and kept until the attempt ends; the last value under a key wins, in the place of the key's first contribution, so the commit follows the order keys were first contributed, as itinera-rs does. On a success they are committed after `step_succeeded`, each emitting `contribution_committed`, then `data_overwritten` when it replaced a value. On a skip they are discarded and `contributions_discarded` follows `step_skipped`, whether or not the step contributed anything. A failure and an abnormal termination commit nothing; a step hook sees a failed attempt's contributions through `@fromStep` (see [0002](0002-foundations.md)). A contribution that is not a value throws the executor's signal at once, since `contribute` returns nothing, and aborts the journey with `not a value`, naming the step and the key.
- **Emitting is in order.** Every call on the step reporter runs once the calls made before it on the same attempt have settled, so a step that does not await a call keeps the specification's order, and the engine waits for every call to settle before it reads the outcome, as the plan's section 6 says. The data of an event and the value of an entry are captured when the call is made, not when its turn comes. A non-value contribution's abort is recorded in its turn too, so what the step emitted before it is delivered and nothing after it. Each promise a call returns has a handler that does nothing attached, so a rejection the step does not await is never unhandled; a step that awaits it still sees it.
- **The executor's signal.** A call that aborts the journey, because its data, its entry or a contribution is not a value, its entry is `journey_id` (`reserved metadata key`), or a reporter or the dispatcher fails on it (`reporter failed`), rejects, or throws for a contribution, with the journey-abort error, of the engine's class `JourneyAbortError`, which the package never exports. A call made once the journey was aborted rejects the same way and delivers nothing. However the step goes on, by catching the error and returning an outcome or by throwing something else, the journey ends aborted, with no outcome fact and no commit.
- **Handles belong to the attempt.** Once `run` and every call it made have settled, the handles are closed, for good: a call then throws an `Error` where it is made, synchronously, saying which handle of which attempt was used, and records, delivers and sets nothing, as chapter 4, 4.6 point 7 says it should. Types cannot stop a step from keeping a handle, so the `@late-handle` scenarios run.
- **What follows an outcome.** A failure emits `step_failed` with its reason, then the executor's own rule decides, in `src/engine/decision.ts`, the same pure function as for an abnormal termination: a retry, `step_retrying` with the cause `failure`, while the retry budget allows another attempt, or `step_given_up`, with the cause `failure` for a step with no budget and `retries exhausted` once a budget is spent, then `journey_failed` carrying the last attempt's reason. A skip goes on to the next step. Planned for stage 6, the decision after a failure lands with the outcome in stage 5, since a failure needs one to end the journey, as the decision after an abnormal termination landed in stage 3. Stage 7 added the hooks around the decision, in `src/engine/outcome.ts` and `src/engine/outcome/failed.ts` (see [0009](0009-running-a-workflow.md)).
- **`StepDescriptor`** and **`StepOptions`** are in [0062](0062-workflow-descriptors.md). A step's name is checked not to be empty, and its retry budget to be a whole number from 0, when it is declared.
- **`Attempt`** moved to `src/step/attempt.ts`, with `nextAttempt`, which only itinera uses and `src/step.ts` does not re-export.

## Tests

- `tests/unit/step.test.ts`: the frozen outcome of success, the outcomes the helpers give, and `Step.builder` refusing a class keeping static data.
- `tests/unit/step/outcome.test.ts`: only outcomes the helpers made are accepted, a reason given as a code or in full, its details captured and turned into plain data, frozen outcomes, and details that are not a value marked.
- `tests/unit/step/declared.test.ts`: what `@step` records, the requests included, and every refusal when a class is defined, static data included, a `private` static field among it.
- `tests/unit/declaration/static-data.test.ts`: a static field, one named by a symbol, an accessor, one returning a function, a field named `name` and a field inherited from a class between the class and its base class refused, each property named, and static methods and the base class's own statics accepted.
- `tests/unit/step/request.test.ts` and `tests/unit/step/request.test-d.ts`: what `@input` and `@stepReporter` record, a type read from the metadata, and what does not compile: a parameter of another type, optional on a parameter that is not an `Option`, no type on a union, a literal, an `Option`, an enum or a branded string, an input on `run` or on a class that is not a step, a step reporter on another method, and data or metadata that is not a value; and what a step hook's requests about its step record, and where they do not compile.
- `tests/unit/journey/contributor.test.ts` and `tests/unit/journey/contributor.test-d.ts`: what `@contributor` records, contributing a value, and what does not compile.
- `tests/unit/engine/build.test.ts` and `tests/unit/engine/request.test.ts`: each input given in order, optional inputs, `classOf`, a copy per step, each abort, the first abort stopping the build, and an abort raised while built passed on.
- `tests/unit/engine/handles.test.ts`: the last value contributed under a key, in order, captured; the events and global metadata a step reporter delivers, in the order of calls not awaited; each abort and what it leaves undelivered; no unhandled rejection; and closed handles throwing and changing nothing.
- `tests/unit/engine/run.test.ts`: the handles lent in the order `run` requests them, calls settled before the outcome, a step that catches the executor's signal still aborted, details that are not a value, closed handles, a request `run` is not lent, what is not an outcome and what is thrown that is not an error.
- `tests/unit/engine/outcome.test.ts`: contributions committed on success, with `data_overwritten`; discarded on a skip; never committed on a failure or an abnormal termination; and the decision after a failure and an abnormal termination, retried or given up.
- `tests/unit/engine/decision.test.ts`: the executor's own rule for every budget, cause and setting.
- `tests/unit/step/descriptor.test.ts`: the needs given to the constructor, the step policies attached, the defaults, the retries given, a new step for every attempt, a frozen descriptor, an empty name and every retry budget that is not a whole number from 0.
- `tests/unit/step/attempt.test.ts`: the attempt, as before.
- `tests/unit/step.test-d.ts`: `Step` is abstract, needs `run`, returns only an outcome or a promise of one, a class that only looks like a step is not one, `@step` marks only a class extending `Step`, and not one keeping static data, nor does `Step.builder`, its own or inherited, though static methods compile, and a reason's details that are not values do not compile.
- `examples/step.ts`, `examples/outcome.ts`, `examples/step-reporter.ts`, `examples/contributor.ts`, and the steps of every example of a workflow.

# 0108: Test support

Tech spec for [proposal 0108](https://github.com/itinera-dev/spec/blob/main/proposals/0108-test-support.md), implemented in [#36](https://github.com/itinera-dev/itinera-ts/issues/36). The [tier 1 plan](../tier-1-plan.md) holds what crosses proposals, section 13 what test support holds and section 14 how the conformance runner uses it.

Status: in progress. Stage 2 added the recording reporter and its path, and started the conformance runner, which uses it. Stage 3 added the step mock and its `Ending`, and made the runner run journeys with them. Stage 5 gave the step mock its inputs and the endings of a failure and a skip, and made the runner build steps with them and play input adapters, then added the reporter that keeps every entry of global metadata, and made the runner play what a step does before it ends. Stage 7 added the policy mocks and their `HookEnding`, and made the runner play policies, hooks and roles with them, and moved the reporter that fails from the runner into test support. Stage 9 added the rescue step mock and its `RescueEnding`. Stage 10 added the subpaths of every concept, then the rest of chapter 8: the mistake in a test, fake providers, scripted runs and recorders. Then the runner played the test support sentences through it.

## API

Test support is the subpath `itinera/testing`, the module `testing`, `src/testing.ts`, with its ESM layer `src/testing.mts`, so that nothing of test support is reachable without importing it, as chapter 8, 8.1 point 2 asks. Until stage 10 listed 0108, it was exported from `itinera/unstable`, which holds nothing now. No other module re-exports it: the recording reporter is a reporter, but `itinera/report` does not offer it.

### The recording reporter

`RecordingReporter`, in `src/testing/recording-reporter.ts`, implements `Reporter` and never fails. It has the three things chapter 8, 8.2 names, as read-only properties in camelCase:

- **`events`**: every event it received, in order, as a new array on each read, so a test changing what it read changes nothing the reporter keeps. The events themselves are the engine's, which freezes them.
- **`globalMetadata`**: each key with its latest value, in the order the keys were first set, as a new `Map` on each read. A `Map` keeps a key set again in its first place, which is what "the latest value of each entry" needs. The journey ID is its first entry, under `journey_id`.
- **`path`**: one line per event of the journey's flow, in order, written as chapter 8, 8.3 writes them. The lines are made by `line(event)`, in `src/testing/recording-reporter/path.ts`, a `switch` over every kind of event, so that a new kind does not compile until it says whether it has a line. An attempt is written by its `number`, a reason by its `code`, a decision by its cause or by the policy of the hook that decided it, and an abort by its reason, with the step when it names one.

### The reporter that keeps every entry

`EntryRecordingReporter`, in `src/testing/entry-recording-reporter.ts`, is one of the mocks beyond chapter 8 that the plan's section 13 adds for the conformance runner. It extends `RecordingReporter`, so it keeps what a recording reporter keeps, and never fails. Its `entries` are every entry of global metadata it received, in order, a key set again included, each a `GlobalMetadataEntry` with the key, the value and `after`, the kind of the event it received last before the entry, as an `Option`: `None` for an entry that came before every event, as the journey ID does. Each read gives a new array.

### The reporter that fails

`FailingReporter`, in `src/testing/failing-reporter.ts`, is the second mock beyond chapter 8 of the plan's section 13. It extends `EntryRecordingReporter`, so it keeps what that reporter keeps, the event or entry it fails on included, then throws an `Error` wherever one of the `ReporterFailure`s it was given says: on the first event, on every event of a kind, or on every entry of global metadata under a key, with the message given or one of its own. `failed` says whether it ever threw. Given no failure, it never fails, which is how the runner makes every reporter of a scenario, failing or not.

### The ending

`Ending`, in `src/testing/ending.ts`, is how a scripted attempt ends, given to a test tool that writes real steps, as chapter 8, 8.5 point 10 asks. It is a discriminated union on `kind`, made by a frozen object of the same name: `Ending.success`, `Ending.failure(reason)`, with a `Reason` or its code alone, `Ending.skip`, `Ending.skipBecause(reason)` and `Ending.abnormalTermination(errorMessage)`. `Ending.outcome(ending)` gives the outcome it stands for: the success outcome, the outcome of a failure or of a skip with its reason, made with the same functions as a step's helpers, or a throw of an `Error` carrying the message, as a step's `run` throws it. A type and an object of one name, rather than a class, keep it a plain discriminated union, as every other union carrying data is.

### The step mock

`stepMock(script)`, in `src/testing/step-mock.ts`, makes a new class extending `StepMock`, itself an abstract class extending `Step`, as "How a mock receives its script" below settles. Its script, `StepMockScript`, says how each attempt ends, the last ending played again by every later attempt, whether `run` gives its outcome through a promise, and the message its constructor throws when it cannot be built. The class counts the steps built from it as attempts, so each workflow takes a class of its own. Its constructor takes any inputs, which the step's builder requests by position with `needs`, and keeps them, in order, as `inputs`, each an `Option` for an optional input. What a scripted attempt does before it ends, contributing, emitting and setting global metadata, is not the step mock's: the conformance runner does it in a subclass of its own, whose `run` takes a contributor and a step reporter by position, and an application's test does it with a scripted run.

`rescueStepMock(script)`, in `src/testing/rescue-step-mock.ts`, makes a new class extending `RescueStepMock`, itself an abstract class extending `RescueStep`, as `stepMock` does for steps. Its script, `RescueStepMockScript`, says the same of a rescue step, each ending a `RescueEnding`, in `src/testing/ending.ts`, which is an `Ending` without the skip, since a rescue step cannot skip, so a script that skips does not compile. Its constructor keeps what it was built with as `inputs`, in order: its inputs, what it requests of the step it rescues, the failure's reason and the error.

### The policy mocks

`stepPolicyMock(script)` and `workflowPolicyMock(script)`, in `src/testing/step-policy-mock.ts` and `src/testing/workflow-policy-mock.ts`, make a new class extending `StepPolicyMock` or `WorkflowPolicyMock`, each an abstract class extending `StepPolicy` or `WorkflowPolicy`, as the step mock does. Each hook is a method of its own, `onStepSuccess`, `onStepFailure`, `onStepRetry` and `onStepAbnormalTermination`, or `onWorkflowSuccess` and `onWorkflowFailure`, taking whatever the builder requests by position. A call keeps, in `calls`, the hook and what it received, in order, then ends as its script says, through a `HookEnding`, in `src/testing/hook-ending.ts`: `HookEnding.keepDefault`, `HookEnding.finishWorkflow`, only for `on step success`, `HookEnding.failWorkflow(reason)`, with a `Reason` or its code alone, for a step hook, and `HookEnding.fail(errorMessage)`, a throw of an `Error`, for any hook; the script's types refuse an ending a hook may not give. A hook the script does not mention keeps the default. `buildFailure` makes the constructor throw an `Error` with that message, so the policy cannot be built. The runner subclasses them to play what a scripted hook does before it ends, in `packages/conformance/src/scenario/policy-mocks.ts`.

### The mistake in a test

`TestMistake`, in `src/testing/mistake.ts`, is the error that chapter 8 calls a mistake in a test: thrown where the mistake is written, or, as a rejection, by a scripted run's `run` before its journey and any event, never a `Refusal`. It extends `Error`, as every error itinera throws does, and its `problems` hold every `Mistake` found, in order, each a discriminated union on `kind`, a value of the closed set `MistakeKind`, with the step, the attempt, the rescued step or the service provider it concerns, as the test named them. Its message names each problem, joined with `; `. A value given to test support that is not a value, such as a contribution a script writes, throws a `TypeError` instead, as the data bag's `with` does, since that is a mistake of types that a cast let through rather than one of chapter 8's.

### Fake providers

`fakeProvider(instance, name, service, fake)`, in `src/testing/fake-provider.ts`, puts `fake` in place of the function of the service provider named `name`, for the journey of that instance alone, and returns the instance. The fake is given `provide`, which makes what a provider's `this.provide(...)` makes, an instance with optional data, and returns it or a promise of it. It is kept on the instance, in a private map of `WorkflowInstance` keyed by provider name, which `useFake` and `fakeOf` in `src/instance/made.ts` reach, so the workflow's descriptor, its admission and its listing are untouched, and the engine's provider call, in `src/engine/provider.ts`, calls the fake where it would call the provider, after the provider's requests are resolved. What it returns is checked as a provider's is, so `service_provided` names the fake's own implementation, and a fake that throws aborts the journey with `step could not be built`. A name the workflow has no provider for, or a service type that is not the provider's, throws a `TestMistake`. Giving a second fake for one provider replaces the first.

### Scripted runs

`scripted(instance)`, in `src/testing/scripted.ts`, starts a script, whose phrases are interfaces in that file and, for what an attempt does, in `src/testing/scripted/attempt.ts`, so that each step of the chain offers only what may follow, as chapter 8, 8.5 orders it: `step` and `andStep`, then `onAttempt`, `onEveryAttempt` or `onRemainingAttempts`, or attempt 1 when none is said, then `willContribute`, `willEmit`, `willSetGlobalMetadata` in that order, then an ending, or `willRunForReal`. `willEmit` takes a `Level`, the closed set of `src/event/level.ts`, which `itinera/event` keeps private and `itinera/testing` re-exports, and optional data, merging `will emit` and `will emit with`, as 8.7 allows. `ensureAllScripted` and `run` follow any ending.

- **Writing.** `Writer`, in `src/testing/scripted/writer.ts`, names steps and runs; `StepWriter`, in `src/testing/scripted/step-writer.ts`, describes the attempts of the step it last named. Each step or rescue step named is a `Target`, in `src/testing/scripted/target.ts`, holding what the workflow says of it, its retry budget, its `retry on abnormal termination` setting, its rescue step, and whether its `run` declares a contributor and a step reporter, and what the script says of its attempts: those numbered, in order, and the rest. Every mistake of 8.5 point 8 throws a `TestMistake` from the call that makes it. A value the script gives is captured when written.
- **Checking.** `leftOut`, in `src/testing/scripted/checks.ts`, lists, before the journey, what 8.5 point 7 says the script leaves out: for each target, the first attempt it can have that is not described, then its rescue step, when attempt 1 can fail and the rescue step is not scripted, then, after `ensureAllScripted`, each step not named. A step can have as many attempts as its retry budget allows, two when it has a rescue step, and a rescue step one. Another attempt can follow a failure or a real run, never a success or a skip, and an abnormal termination only on attempt 1 of a step with a rescue step or when the step retries abnormal terminations.
- **Playing.** `run(executor?)` runs the journey on the executor given, or a new `LocalExecutor`, through `runScripted`, in `src/executor/local.ts`, which reaches the executor's private run with a `Scripting`, an interface of the engine, in `src/engine/script.ts`. The engine tells the script, in `src/engine/build.ts`, each attempt handed to its step's construction, with the values its inputs found and, for a rescue step, the contributions it requested, just before the constructor is called, and asks it, in `src/engine/run.ts`, what an attempt plays in place of the step's `run`. `playing`, in `src/testing/scripted/play.ts`, answers: the actions of a described attempt, in order, through the contributor and step reporter the attempt lends, then the outcome its `Ending` stands for. Everything else of the journey, building the step included, is the engine's own, so a scripted ending has a real one's consequences.
- **The record.** `ScriptedRun`, `StepRecord` and `AttemptRecord`, in `src/testing/scripted/record.ts`, are classes only itinera makes. `step(name)` reads the record of any step or rescue step of the workflow, those the journey never reached included, and throws a `TestMistake` for another name. `attempts` holds every attempt handed to the construction of its step, in order; `attempt(number)` reads one as an `Option`; and an attempt's record holds its `Attempt`, and its `input(key, type)` reads the values its step was built with, as the data bag's `read` does.

### Recorders

`Contributions`, `StepEventReporter` and `HookEventReporter`, in `src/testing/recorders.ts`, lend the handles of chapter 8, 8.6 outside any journey. Each lends the engine's own handles, of a lone journey made in `src/testing/lone.ts`, whose dispatcher keeps what it is given, or, made `failing`, throws on every call, so each handle behaves as in a journey: a failing recorder interrupts every call and keeps nothing, and setting `journey_id` interrupts that call and every later one. `Contributions` reads what was contributed with `read` and `keys`; each reporter recorder keeps every event emitted, as an `Emitted` with its `Level`, message and data, and the global metadata set. `TestDataBag`, in `src/testing/test-data-bag.ts`, builds a data bag from values with `with`, captured when given, and lends its read access with `access`, named apart from the journey's `DataBag`, which only itinera makes.

## Dependencies

None of its own.

## The conformance runner

Stage 2 started the runner in `packages/conformance`, on cucumber-js 13.3.0, with `@cucumber/tag-expressions` 11.0.1 to refuse a tag expression that does not parse before anything runs. It is a package of the workspace that is never published, so neither is a dependency of `itinera`.

- **Compiled, not stripped.** `npm run conformance` builds `itinera` and the runner with `tsc`, then runs `packages/conformance/dist/main.js`, which loads `dist/support.js` into cucumber. The fixtures of later stages use legacy decorators with `emitDecoratorMetadata`, which neither Node's type stripping nor esbuild emits, so the runner is compiled as `itinera` is. It imports the subpaths of the concepts, test support from `itinera/testing`, and `itinera/schema` for Zod, through the workspace's link to the built package, the path an application takes.
- **The environment** is read by `readEnvironment`, in `src/environment.ts`: the three variables are required and none may be empty, and the tag expression must parse.
- **The scenario model**, in `src/model.ts` and its submodules, holds what the Given sentences declare as plain data: the workflow and its steps' scripts, the initial data and global metadata, how scripted reporters fail, and what the executor is given to dispatch events. A sentence that does not fit the model, such as a step scripted before the workflow is declared, throws a `ModelError`, an error in the case.
- **The sentences** are those of STEPS.md, registered in `src/sentences/`, one file per section of the catalogue, with the Then sentences of Outcomes, and of Events and reporters, split in `src/sentences/outcomes/` and `src/sentences/reporters/`. Stage 2 defined the sentences that only declare: building a workflow, data, journey IDs, the Given sentences of events and reporters and of global metadata, and a step being asynchronous. Stage 3 adds the When sentences that admit and run the workflow, once or twice on one executor, and the Then sentences of Outcomes, Events, Events and reporters and The executor that read what a journey did: how it ended, its result's failure or abort, its journey ID, each step's status, how often a step was built, the event tables, what each reporter received, and what no event carries. Stage 5 adds the Given sentences of input adapters, the Then sentences of what a step was built with, for every attempt or for one, and the result's data bag holding values, then the Then sentences of the global metadata reporters received, the same for several reporters, no contribution of a key committed, and no engine event carrying a value of global metadata. Stage 6 adds the Then sentence of a reporter made with the journey ID. Stage 7 adds the sentences of policies, in `src/sentences/policies.ts`, of what hooks do, in `src/sentences/hooks.ts`, of what they were called with and what roles saw, in `src/sentences/outcomes/hooks.ts` and `src/sentences/outcomes/hooks/`, the When sentence that lists the workflow and the Then sentence of its listing, in `src/sentences/outcomes/listing.ts`, and the Then sentence that reads the second journey's data bag. The sentences of services and test support come with the stages that run them. Until then their scenarios are undefined, which fails them, as a strict run does.
- **The workflow** of a scenario is put together with the builder, in `src/scenario.ts`, on a `Scenario` class, in `src/scenario/workflow.ts`, that declares nothing, each step a class `stepMock` makes from the step's script and the witness, in `src/witness.ts`, keeps every step built and every step that ran. Each step's inputs are given to its builder by position, typed by `src/tokens.ts`, which maps each type of the neutral vocabulary to itinera's token. A value the scenario gives is made what itinera receives by `src/given.ts`. Every input adapter the scenario declares is the method `adapt` of `Scenario`, named to the builder under the adapter's name, with the step name, the key and the adapter's own requests, in the order its sentences are written, by position: one method serves every adapter, since admission refuses two adapters on one step, so the step it is called for says which adapter's script it plays. `Adapters`, in `src/adapters.ts`, plays it: it returns what the script says, reads through the access it requested or through one it kept from an earlier call, and writes through it as far as TypeScript allows, which is setting a property of the object, since `DataBag` has no method that writes. A script that uses an access the adapter does not request, or reads through a kept access it never keeps, throws a `ModelError` when the workflow is built, since a throw inside the adapter would reach the journey as the adapter failing. `src/scenario/mock.ts` makes a step mock's script of each step's script, each ending a success, a failure with its reason or a skip, with its reason if it gives one. The witness extends the class `stepMock` makes with a `run` that takes a contributor and a step reporter by position and, before the mock's `run` ends the attempt, plays what `src/scenario/actions.ts` makes of the script: its contributions, emits, entries of global metadata and changes to an input, in the order the sentences are written, awaiting each call to the step reporter, and catching a failed emit when the step ignores such failures, then the contributions of the attempt's row. A script that changes an input the step never requests throws a `ModelError` when the workflow is built. The scenario's policies, in `src/scenario/policies.ts` and `src/scenario/policy-mocks.ts`, are classes test support's policy mocks make, each hook given the contributor, the hook reporter, then its scripted requests by position, which plays what `src/scenario/hooks.ts` makes of the script before the mock ends the call: its contributions, a count of its calls, changes to the step data it received, emits, entries of global metadata, calls of a role's operation, and calls on the handles a step kept, each refused, since its attempt ended. `Scenario` provides every role the scenario declares through one method, `perform`, which `src/roles.ts` plays, counting each call of an operation and throwing where the scenario says it does; the witness keeps every call of a hook, in order, in `src/witness/hooks.ts`. Each rescue step, in `src/scenario/rescue.ts`, is a class `rescueStepMock` makes from its script, which the witness extends as it does a step's, its constructor given its inputs, then what it requests of the step it rescues, by position, and the witness keeps every rescue step built; a script saying that a rescue step skips throws a `ModelError` when the workflow is built, since a rescue step cannot skip.
- **The stream** a sentence reads follows FORMAT.md: the events the reporter held by the runner's dispatchers received of the journey, or, under the default dispatcher, the events of the first reporter the workflow lists that never failed, made for that journey (`src/journeys.ts`). A sentence about the whole stream reads the last journey that ran.
- **The trace**, in `src/trace.ts` and `src/trace/`, writes each event as a line of an event table, a `switch` over every kind of event, reads the line a table's row expects, compares lines in order or exactly, finds a message or a value an event carries, and reads each step's status and attempts from the events.
- **What a sentence expected and itinera did not do** throws `Unmet`, a failure of the implementation, while a sentence that does not fit the scenario throws `ModelError`, an error in the case.
- **The recording dispatcher factory**, `RecordingDispatcherFactory` in `src/record.ts`, makes the dispatchers the executor is given: each delivers through a `DefaultDispatcher` to the reporter it holds first, then to the reporters it accepts, or fails as the scenario scripts it: when it is made, when a reporter is added, or when it dispatches an event of one kind. The reporter it holds is the one it is given: a `ScenarioReporter`, in `src/recorders.ts`, test support's `FailingReporter`, which fails as the scenario scripts it and remembers whether it failed, keeping the journey ID it was made with. The scenario's world keeps every one under its name, the runner's own as "the runner's recorder", and makes one for each journey of a reporter the workflow lists: the workflow instance makes it, as one of its own reporters, a function of the journey ID, so the reporter keeps the ID it was made with, which the sentence "the reporter was made with the journey ID" reads.
- **Test support's sentences**, in `src/sentences/testing.ts`, `src/sentences/scripted.ts`, `src/sentences/alone.ts` and `src/sentences/alone/kept.ts`, reach every part through `itinera/testing`. The model keeps what they declare in `TestSupport`, in `src/model/testing.ts`, with a script's rows read by `src/model/testing/script.ts`. `Tested`, in `src/tested.ts`, makes each instance with test support's recording reporter last, when the scenario adds it, and with the fakes of `Fakes`, in `src/fakes.ts`, which count every call and label each instance `fake <n>`, counting the fake's calls in the journey, and keeps the `TestMistake` that stops the test, from a Given's declaration or the When sentence alike, and the scripted run's record. `runScript`, in `src/script.ts`, writes the script row by row, naming a step with `step`, then with `andStep` whenever the step changes, and runs it on a `LocalExecutor` without a dispatcher factory, the runner's recorder being the instance's first reporter, so the sentences about the stream read it as for any journey. `Alone`, in `src/alone.ts`, builds a step outside any journey from the witness's class and calls its `run`, calls a hook on a new object of its policy's class (`src/alone/hook.ts`), or calls the workflow's `adapt` with the access of a `TestDataBag`, each with the handles the recorders lend, made failing as the scenario says. `CarryingOn`, in `src/alone/carrying-on.ts`, lends a copy of each handle that records every call and carries on after one that throws or rejects, marking it interrupted. A step mock's `run` takes its handles as a rest parameter, so that a step that declares no contributor and no reporter needs no request.
- **The report** is cucumber-js's JSON formatter, writing to `ITINERA_CONFORMANCE_REPORT`, and only the selected scenarios are in it. The summary formatter writes to standard output.

## How a mock receives its script

Settled in stage 3, as a default the maintainer may change, and built by `stepMock`: a function of test support makes a new class for each scripted step, extending the step mock's own class, which extends `Step`, and closing over the step's script, so the builder is given a class, as it requires, and builds it anew for every attempt, which reads its script from the closure. The builder takes a class extending `Step` through another class, which `@step` does not. When stage 4 gives steps requests, the runner gives a mock's requests to the builder by position, as `needs` and `run` in its step options, as it may for any class, so the requests of the mock's own class, recorded under that class, are never looked up for the class made per scenario. A policy mock is made the same way, in the stage whose scenarios first need one.

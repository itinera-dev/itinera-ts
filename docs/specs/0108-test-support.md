# 0108: Test support

Tech spec for [proposal 0108](https://github.com/itinera-dev/spec/blob/main/proposals/0108-test-support.md), implemented in [#36](https://github.com/itinera-dev/itinera-ts/issues/36). The [tier 1 plan](../tier-1-plan.md) holds what crosses proposals, section 13 what test support holds and section 14 how the conformance runner uses it.

Status: in progress. Stage 2 added the recording reporter and its path, and started the conformance runner, which uses it. Stage 3 added the step mock and its `Ending`, and made the runner run journeys with them. Stage 5 gave the step mock its inputs and the endings of a failure and a skip, and made the runner build steps with them and play input adapters, then added the reporter that keeps every entry of global metadata, and made the runner play what a step does before it ends. The policy mock and the reporter that fails come with the first scenarios that need them, the rest of chapter 8 in stage 10, which lists the proposal and claims `testing`.

## API

Until 0108 is listed, test support is exported only from `itinera/unstable`. It lives in the module `testing`, `src/testing.ts`, which becomes the subpath `itinera/testing` in stage 10, so that nothing of test support is reachable without importing it, as chapter 8, 8.1 point 2 asks. No other module re-exports it: the recording reporter is a reporter, but `itinera/report` does not offer it.

### The recording reporter

`RecordingReporter`, in `src/testing/recording-reporter.ts`, implements `Reporter` and never fails. It has the three things chapter 8, 8.2 names, as read-only properties in camelCase:

- **`events`**: every event it received, in order, as a new array on each read, so a test changing what it read changes nothing the reporter keeps. The events themselves are the engine's, which freezes them.
- **`globalMetadata`**: each key with its latest value, in the order the keys were first set, as a new `Map` on each read. A `Map` keeps a key set again in its first place, which is what "the latest value of each entry" needs. The journey ID is its first entry, under `journey_id`.
- **`path`**: one line per event of the journey's flow, in order, written as chapter 8, 8.3 writes them. The lines are made by `line(event)`, in `src/testing/recording-reporter/path.ts`, a `switch` over every kind of event, so that a new kind does not compile until it says whether it has a line. An attempt is written by its `number`, a reason by its `code`, a decision by its cause or by the policy of the hook that decided it, and an abort by its reason, with the step when it names one.

### The reporter that keeps every entry

`EntryRecordingReporter`, in `src/testing/entry-recording-reporter.ts`, is one of the mocks beyond chapter 8 that the plan's section 13 adds for the conformance runner. It extends `RecordingReporter`, so it keeps what a recording reporter keeps, and never fails. Its `entries` are every entry of global metadata it received, in order, a key set again included, each a `GlobalMetadataEntry` with the key, the value and `after`, the kind of the event it received last before the entry, as an `Option`: `None` for an entry that came before every event, as the journey ID does. Each read gives a new array.

### The ending

`Ending`, in `src/testing/ending.ts`, is how a scripted attempt ends, given to a test tool that writes real steps, as chapter 8, 8.5 point 10 asks. It is a discriminated union on `kind`, made by a frozen object of the same name: `Ending.success`, `Ending.failure(reason)`, with a `Reason` or its code alone, `Ending.skip`, `Ending.skipBecause(reason)` and `Ending.abnormalTermination(errorMessage)`. `Ending.outcome(ending)` gives the outcome it stands for: the success outcome, the outcome of a failure or of a skip with its reason, made with the same functions as a step's helpers, or a throw of an `Error` carrying the message, as a step's `run` throws it. A type and an object of one name, rather than a class, keep it a plain discriminated union, as every other union carrying data is.

### The step mock

`stepMock(script)`, in `src/testing/step-mock.ts`, makes a new class extending `StepMock`, itself an abstract class extending `Step`, as "How a mock receives its script" below settles. Its script, `StepMockScript`, says how each attempt ends, the last ending played again by every later attempt, whether `run` gives its outcome through a promise, and the message its constructor throws when it cannot be built. The class counts the steps built from it as attempts, so each workflow takes a class of its own. Its constructor takes any inputs, which the step's builder requests by position with `needs`, and keeps them, in order, as `inputs`, each an `Option` for an optional input. What a scripted attempt does before it ends, contributing, emitting and setting global metadata, comes with scripted runs in stage 10; until then the conformance runner does it in a subclass of its own, whose `run` takes a contributor and a step reporter by position.

## Dependencies

None of its own.

## The conformance runner

Stage 2 started the runner in `packages/conformance`, on cucumber-js 13.3.0, with `@cucumber/tag-expressions` 11.0.1 to refuse a tag expression that does not parse before anything runs. It is a package of the workspace that is never published, so neither is a dependency of `itinera`.

- **Compiled, not stripped.** `npm run conformance` builds `itinera` and the runner with `tsc`, then runs `packages/conformance/dist/main.js`, which loads `dist/support.js` into cucumber. The fixtures of later stages use legacy decorators with `emitDecoratorMetadata`, which neither Node's type stripping nor esbuild emits, so the runner is compiled as `itinera` is. It imports `itinera/unstable`, and `itinera/schema` for Zod, through the workspace's link to the built package, the path an application takes.
- **The environment** is read by `readEnvironment`, in `src/environment.ts`: the three variables are required and none may be empty, and the tag expression must parse.
- **The scenario model**, in `src/model.ts` and its submodules, holds what the Given sentences declare as plain data: the workflow and its steps' scripts, the initial data and global metadata, how scripted reporters fail, and what the executor is given to dispatch events. A sentence that does not fit the model, such as a step scripted before the workflow is declared, throws a `ModelError`, an error in the case.
- **The sentences** are those of STEPS.md, registered in `src/sentences/`, one file per section of the catalogue, with the Then sentences of Outcomes, and of Events and reporters, split in `src/sentences/outcomes/` and `src/sentences/reporters/`. Stage 2 defined the sentences that only declare: building a workflow, data, journey IDs, the Given sentences of events and reporters and of global metadata, and a step being asynchronous. Stage 3 adds the When sentences that admit and run the workflow, once or twice on one executor, and the Then sentences of Outcomes, Events, Events and reporters and The executor that read what a journey did: how it ended, its result's failure or abort, its journey ID, each step's status, how often a step was built, the event tables, what each reporter received, and what no event carries. Stage 5 adds the Given sentences of input adapters, the Then sentences of what a step was built with, for every attempt or for one, and the result's data bag holding values, then the Then sentences of the global metadata reporters received, the same for several reporters, no contribution of a key committed, and no engine event carrying a value of global metadata. Stage 6 adds the Then sentence of a reporter made with the journey ID. The sentences of policies, hooks and roles, services and test support, and the Then sentence that reads the second journey's data bag, come with the stages that run them. Until then their scenarios are undefined, which fails them, as a strict run does.
- **The workflow** of a scenario is put together with the builder, in `src/scenario.ts`, on a `Scenario` class that declares nothing, each step a class `stepMock` makes from the step's script and the witness, in `src/witness.ts`, keeps every step built and every step that ran. Each step's inputs are given to its builder by position, typed by `src/tokens.ts`, which maps each type of the neutral vocabulary to itinera's token. A value the scenario gives is made what itinera receives by `src/given.ts`. Every input adapter the scenario declares is the method `adapt` of `Scenario`, named to the builder under the adapter's name, with the step name, the key and the adapter's own requests, in the order its sentences are written, by position: one method serves every adapter, since admission refuses two adapters on one step, so the step it is called for says which adapter's script it plays. `Adapters`, in `src/adapters.ts`, plays it: it returns what the script says, reads through the access it requested or through one it kept from an earlier call, and writes through it as far as TypeScript allows, which is setting a property of the object, since `DataBag` has no method that writes. A script that uses an access the adapter does not request, or reads through a kept access it never keeps, throws a `ModelError` when the workflow is built, since a throw inside the adapter would reach the journey as the adapter failing. `src/scenario/mock.ts` makes a step mock's script of each step's script, each ending a success, a failure with its reason or a skip, with its reason if it gives one. The witness extends the class `stepMock` makes with a `run` that takes a contributor and a step reporter by position and, before the mock's `run` ends the attempt, plays what `src/scenario/actions.ts` makes of the script: its contributions, emits, entries of global metadata and changes to an input, in the order the sentences are written, awaiting each call to the step reporter, and catching a failed emit when the step ignores such failures, then the contributions of the attempt's row. A script that changes an input the step never requests throws a `ModelError` when the workflow is built. A script the runner cannot run yet, such as a rescue step or a kept handle, throws `NotRunYet` when the workflow is built, which fails the scenario saying what it could not run; each stage that makes such a script run removes it from the list.
- **The stream** a sentence reads follows FORMAT.md: the events the reporter held by the runner's dispatchers received of the journey, or, under the default dispatcher, the events of the first reporter the workflow lists that never failed, made for that journey (`src/journeys.ts`). A sentence about the whole stream reads the last journey that ran.
- **The trace**, in `src/trace.ts` and `src/trace/`, writes each event as a line of an event table, a `switch` over every kind of event, reads the line a table's row expects, compares lines in order or exactly, finds a message or a value an event carries, and reads each step's status and attempts from the events.
- **What a sentence expected and itinera did not do** throws `Unmet`, a failure of the implementation, while a sentence that does not fit the scenario throws `ModelError`, an error in the case.
- **The recording dispatcher factory**, `RecordingDispatcherFactory` in `src/record.ts`, makes the dispatchers the executor is given: each delivers through a `DefaultDispatcher` to the reporter it holds first, then to the reporters it accepts, or fails as the scenario scripts it: when it is made, when a reporter is added, or when it dispatches an event of one kind. The reporter it holds is the one it is given: a `ScenarioReporter`, in `src/recorders.ts`, an `EntryRecordingReporter` that fails as the scenario scripts it and remembers whether it failed. The scenario's world keeps every one under its name, the runner's own as "the runner's recorder", and makes one for each journey of a reporter the workflow lists: the workflow instance makes it, as one of its own reporters, a function of the journey ID, so the reporter keeps the ID it was made with, which the sentence "the reporter was made with the journey ID" reads.
- **The report** is cucumber-js's JSON formatter, writing to `ITINERA_CONFORMANCE_REPORT`, and only the selected scenarios are in it. The summary formatter writes to standard output.

## How a mock receives its script

Settled in stage 3, as a default the maintainer may change, and built by `stepMock`: a function of test support makes a new class for each scripted step, extending the step mock's own class, which extends `Step`, and closing over the step's script, so the builder is given a class, as it requires, and builds it anew for every attempt, which reads its script from the closure. The builder takes a class extending `Step` through another class, which `@step` does not. When stage 4 gives steps requests, the runner gives a mock's requests to the builder by position, as `needs` and `run` in its step options, as it may for any class, so the requests of the mock's own class, recorded under that class, are never looked up for the class made per scenario. A policy mock is made the same way, in the stage whose scenarios first need one.

# 0010: Hooks, lifecycles and workflow roles

Tech spec for [proposal 0010](https://github.com/itinera-dev/spec/blob/main/proposals/0010-hooks-lifecycles-and-roles.md), implemented in [#6](https://github.com/itinera-dev/itinera-ts/issues/6). The [tier 1 plan](../tier-1-plan.md) holds what crosses proposals, section 7 the policies, hooks and roles, [0041](0041-hook-data-from-the-data-bag.md) a hook's data from the workflow, and [0062](0062-workflow-descriptors.md) the table of requests and the descriptors.

Status: in progress. Stage 1 added the hooks' names, the lifecycles events carry and the retry causes. Stage 4 has added the base classes, the hooks' decorators, what a hook returns, `@stepPolicy` and `@workflowPolicy`, the requests only hooks make, and the roles checked when policies are attached. Its next layer adds policy descriptors and the violations about hooks, and stage 7 calls the hooks and lists the proposal.

## API

Until 0010 is listed, everything here is exported only from `itinera/unstable`. It is defined in `src/policy.ts`, which becomes the subpath `itinera/policy` then, with its submodules in `src/policy/`.

- **`StepPolicy<R>`** and **`WorkflowPolicy<R>`** are abstract. Each has an ECMAScript private brand, `#stepPolicy` or `#workflowPolicy`, so neither is structurally the other, and only a subclass has the type of a policy. `R`, the roles the policy requests, is a covariant phantom, `declare readonly [roles]: R`, under a `unique symbol` only itinera names, as the plan's notes 3 and 7 require: it exists only in the types, and a `protected` member would let every workflow pass. `StepPolicyClass<R>` and `WorkflowPolicyClass<R>` are the classes, constructed with no arguments.
- **What a hook returns.** `StepPolicy` gives its subclasses `this.keepDefault()`, `this.finishWorkflow()` and `this.failWorkflow(reason)`, where a reason is a `Reason` or only its code, as chapter 6, 6.11 suggests. `keepDefault` and `finishWorkflow` return frozen singletons, and `failWorkflow` a frozen `FailWorkflow`. `KeepDefault` is `{ kind: "KeepDefault" }`, not a lifecycle, so `hook_called` records none. `OnSuccess` is `KeepDefault | FinishWorkflow | FailWorkflow`, and `OnFailure` is `KeepDefault | FailWorkflow`.
- **The hooks' decorators**, in `src/policy/hooks.ts`: `@onStepSuccess()`, `@onStepFailure()`, `@onStepRetry()`, `@onStepAbnormalTermination()`, `@onWorkflowSuccess()` and `@onWorkflowFailure()`. Each is a `HookDecorator<R, P>`, generic in the method's type, since `TypedPropertyDescriptor<M>` is invariant (note 1), and compiles only on a method of a policy of kind `P` returning `R` or a promise of it: `OnSuccess`, `OnFailure`, or `void` for a workflow hook, written `void | Promise<void>` so that a method returning a value does not fit (note 2). So a failure hook returning `this.finishWorkflow()` does not compile, which is the rule `invalid-lifecycle` made impossible; its proof and its entry under `impossible` land in stage 7, with the engine's check of what a hook returned through a cast. Each records the hook and its method, keyed by the class, and requires the compiler's metadata. One hook on two methods, or two hooks on one method, throws when the class is defined.
- **`@stepPolicy(options?)`** and **`@workflowPolicy(options?)`**, in `src/policy/declared.ts`, take a class extending their base class whose constructor takes nothing, `new () => StepPolicy` or `new () => WorkflowPolicy`. The name is the class's name unless `options.name` gives one; the documentation advises naming it, since minifiers rename classes. Each records, in a `WeakMap` keyed by the class, the policy's name and each hook with its method and its requests. When the class is defined, each throws if the class does not extend its base class itself, if it is declared twice, if its name is empty, if it defines no hook, if a method carries requests but no hook, if a parameter of a hook has no request, or if a hook requests a cause it is not given. That last check cannot be typed, since a parameter decorator cannot see its method's decorator.
- **The requests only hooks make.** Each compiles only in its place and on a parameter whose type accepts what it gives:
  - `@fromStep(key, type?)`, data from the step, in a step policy, typed like `@input`;
  - `@role<R>()` in a policy whose base class's type argument names `R`, giving the workflow object as `R`;
  - `@failureCause()`, giving a `StepFailureCause`, and `@retryCause()`, giving a `RetryCause`, both in a step policy;
  - `@hookReporter()`, giving a `HookReporter`, whose `info`, `warning` and `error` emit `journey_info`, `journey_warning` and `journey_error`, and whose `setGlobalMetadata` sets global metadata, each returning a promise, in either kind of policy.

  The requests of a step hook about its step, `@stepName()`, `@attempt()`, `@failureReason(options?)` and `@error(options?)`, are in [0008](0008-steps.md); `@journeyId()` is in `itinera/journey`; `@fromWorkflow` is in [0041](0041-hook-data-from-the-data-bag.md); and `@contributor()` now also compiles in a hook.
- **Asking what a hook returned.** Chapter 6, 6.11 point 1.3 suggests that what a step hook returns can be asked whether it keeps the default, finishes the workflow or fails it. Here it is a discriminated union on `kind`, which a test matches on; readers that ask it, as Rust's do, are left to stage 10, with test support, which decides their names.
- **Policy instances are not frozen.** Chapter 6, 6.1 point 7 asks for a policy instance read-only inside a hook where the language can make it so. TypeScript cannot: `Object.freeze` is shallow, does not reach private fields, and would turn a hook that changes its policy into `hook failed`. So the point falls to its last sentence: stage 7 builds the instances anew, workflow policies once per journey and step policies for every attempt, so no change a hook makes outlives the journey or the attempt.
- **`StepFailureCause`** is `FailureCause` without `FailWorkflow`, since `on step failure` is not called after a hook returned `FailWorkflow`.
- **Roles.** `RolesOf<P>` joins with `&` the roles every policy of a list written in place requests, by recursion over the tuple, since a union with `unknown`, which a policy that requests no role has, would absorb the others. For the same reason it never joins with `|`: a list that may be one of several, such as `flag ? [Notify] : []`, or a policy that may be one of several, such as `[flag ? Notify : Quiet]`, gives the roles of every one of them, which the compiler infers from where a union of functions takes them. A list whose length the compiler cannot see gives `never`, so no workflow compiles with it. `@withStep(step, { policies })` and `@workflow({ policies })` take `const` type parameters, so a list written in place is a tuple, and return a decorator that takes only a `WorkflowClass<RolesOf<P>>`, a class extending `Workflow` whose objects implement those roles. So a policy attached to a workflow that does not provide its roles does not compile, which is the rule `role-not-provided` made impossible; its proof and its entry under `impossible` land in stage 7. Each decorator also refuses, when the class is defined, a policy not declared with `@stepPolicy` or `@workflowPolicy`, and a policy of the other kind given through a cast, since each policy's declaration records its kind. The builder attaches no policies until the next layer, so its step options take an empty list only.

- `src/workflow/decorators.test-d.ts`: a workflow that implements every role its policies request, one that does not, a list or a policy that may be one that requests a role, a policy of the other kind, and a list not written in place.

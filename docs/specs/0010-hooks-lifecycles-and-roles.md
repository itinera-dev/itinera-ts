# 0010: Hooks, lifecycles and workflow roles

Tech spec for [proposal 0010](https://github.com/itinera-dev/spec/blob/main/proposals/0010-hooks-lifecycles-and-roles.md), implemented in [#6](https://github.com/itinera-dev/itinera-ts/issues/6). The [tier 1 plan](../tier-1-plan.md) holds what crosses proposals, section 7 the policies, hooks and roles, [0041](0041-hook-data-from-the-data-bag.md) a hook's data from the workflow, and [0062](0062-workflow-descriptors.md) the table of requests and the descriptors.

Status: complete, and 10 is listed in `conformance.json`. Stage 1 added the hooks' names, the lifecycles events carry and the retry causes. Stage 4 has added the base classes, the hooks' decorators, what a hook returns, `@stepPolicy` and `@workflowPolicy`, the requests only hooks make, and the roles checked when policies are attached. Its sixth layer has added policy descriptors and a builder for each kind of policy, its seventh has added the violations about hooks, and stage 7 called the hooks, checked what they return, gave them the workflow as their roles, added the policy mocks of test support, and listed the proposal.

## API

Since stage 10, its API is exported from the subpaths of its concepts, chiefly `itinera/policy`, and its test support from `itinera/testing`. It is defined in `src/policy.ts`, with its submodules in `src/policy/`.

- **`StepPolicy<R>`** and **`WorkflowPolicy<R>`** are abstract. Each has an ECMAScript private brand, `#stepPolicy` or `#workflowPolicy`, so neither is structurally the other, and only a subclass has the type of a policy. `R`, the roles the policy requests, is a covariant phantom, `declare readonly [roles]: R`, under a `unique symbol` only itinera names, as the plan's notes 3 and 7 require: it exists only in the types, and a `protected` member would let every workflow pass. `StepPolicyClass<R>` and `WorkflowPolicyClass<R>` are the classes, constructed with no arguments.
- **What a hook returns.** `StepPolicy` gives its subclasses `this.keepDefault()`, `this.finishWorkflow()` and `this.failWorkflow(reason)`, where a reason is a `Reason` or only its code, as chapter 6, 6.11 suggests. `keepDefault` and `finishWorkflow` return frozen singletons, and `failWorkflow` a frozen `FailWorkflow`. `KeepDefault` is `{ kind: "KeepDefault" }`, not a lifecycle, so `hook_called` records none. `OnSuccess` is `KeepDefault | FinishWorkflow | FailWorkflow`, and `OnFailure` is `KeepDefault | FailWorkflow`.
- **The hooks' decorators**, in `src/policy/hooks.ts`: `@onStepSuccess()`, `@onStepFailure()`, `@onStepRetry()`, `@onStepAbnormalTermination()`, `@onWorkflowSuccess()` and `@onWorkflowFailure()`. Each is a `HookDecorator<R, P>`, generic in the method's type, since `TypedPropertyDescriptor<M>` is invariant (note 1), and compiles only on a method of a policy of kind `P` returning `R` or a promise of it: `OnSuccess`, `OnFailure`, or `void` for a workflow hook, written `void | Promise<void>` so that a method returning a value does not fit (note 2). So a failure hook returning `this.finishWorkflow()` does not compile, which is the rule `invalid-lifecycle` made impossible; its proof and its entry under `impossible` are in [0054](0054-how-custom-code-fails.md), with the engine's check of what a hook returned through a cast. Each records the hook and its method, keyed by the class, and requires the compiler's metadata. One hook on two methods, or two hooks on one method, throws when the class is defined.
- **`@stepPolicy(options?)`** and **`@workflowPolicy(options?)`**, in `src/policy/declared.ts`, take a class extending their base class whose constructor takes nothing, `new () => StepPolicy` or `new () => WorkflowPolicy`. The name is the class's name unless `options.name` gives one; the documentation advises naming it, since minifiers rename classes. Each records, in a `WeakMap` keyed by the class, the policy's name and each hook with its method and its requests. When the class is defined, each throws if the class does not extend its base class itself, if it is declared twice, if its name is empty, if it defines no hook, if a method carries requests but no hook, if a parameter of a hook has no request, or if a hook requests a cause it is not given. That last check cannot be typed, since a parameter decorator cannot see its method's decorator.
- **The requests only hooks make.** Each compiles only in its place and on a parameter whose type accepts what it gives:
  - `@fromStep(key, type?)`, data from the step, in a step policy, typed like `@input`;
  - `@role<R>()` in a policy whose base class's type argument names `R`, giving the workflow object as `R`;
  - `@failureCause()`, giving a `StepFailureCause`, and `@retryCause()`, giving a `RetryCause`, both in a step policy;
  - `@hookReporter()`, giving a `HookReporter`, whose `info`, `warning` and `error` emit `journey_info`, `journey_warning` and `journey_error`, and whose `setGlobalMetadata` sets global metadata, each returning a promise, in either kind of policy.

  The requests of a step hook about its step, `@stepName()`, `@attempt()`, `@failureReason(options?)` and `@error(options?)`, are in [0008](0008-steps.md); `@journeyId()` is in `itinera/journey`; `@fromWorkflow` is in [0041](0041-hook-data-from-the-data-bag.md); and `@contributor()` now also compiles in a hook.
- **Asking what a hook returned.** Chapter 6, 6.11 point 1.3 suggests that what a step hook returns can be asked whether it keeps the default, finishes the workflow or fails it. Here it is a discriminated union on `kind`, which a test matches on; readers that ask it, as Rust's do, are left to stage 10, with test support, which decides their names.
- **Policy instances are not frozen.** Chapter 6, 6.1 point 7 asks for a policy instance read-only inside a hook where the language can make it so. TypeScript cannot: `Object.freeze` is shallow, does not reach private fields, and would turn a hook that changes its policy into `hook failed`. So the point falls to its last sentence: the engine builds the instances anew (see [0058](0058-building-policies.md)), workflow policies once per journey and step policies for every attempt, so no change a hook makes outlives the journey or the attempt.
- **`StepFailureCause`** is `FailureCause` without `FailWorkflow`, since `on step failure` is not called after a hook returned `FailWorkflow`.
- **Roles.** `RolesOf<P>` joins with `&` the roles every policy of a list written in place requests, by recursion over the tuple, since a union with `unknown`, which a policy that requests no role has, would absorb the others. For the same reason it never joins with `|`: a list that may be one of several, such as `flag ? [Notify] : []`, or a policy that may be one of several, such as `[flag ? Notify : Quiet]`, gives the roles of every one of them, which the compiler infers from where a union of functions takes them. A list whose length the compiler cannot see gives `never`, so no workflow compiles with it. `@withStep(step, { policies })` and `@workflow({ policies })` take `const` type parameters, so a list written in place is a tuple, and return a decorator that takes only a `WorkflowClass<RolesOf<P>>`, a class extending `Workflow` whose objects implement those roles. So a policy attached to a workflow that does not provide its roles does not compile, which is the rule `role-not-provided` made impossible; its proof and its entry under `impossible` are in [0054](0054-how-custom-code-fails.md). Each decorator also refuses, when the class is defined, a policy not declared with `@stepPolicy` or `@workflowPolicy`, and a policy of the other kind given through a cast, since each policy's declaration records its kind. The builders check the same roles: a step's builder, `StepBuilder<C, R>`, gathers in `R` the roles of each policy its `policy(...)` attaches, and the workflow builder's `step(builder)` and `policy(...)` take a parameter typed with `Provides<InstanceType<C>, R>`, which is `unknown` when the workflow implements `R` and otherwise the string literal `"the workflow class does not implement the roles its policies request"`, so the call does not compile.
- **Policy descriptors.** `PolicyDescriptor`, in `src/policy/descriptor.ts`, is sealed as the step descriptor is: a class with a private constructor, which only `describePolicy` makes, holding the policy's name, its kind, its class and each hook with its method and its requests. Its public members are `name`, `hooks()`, the hooks the policy defines in the order they were declared, and `build()`, which makes a new policy object. `@stepPolicy` and `@workflowPolicy` keep one in their `WeakMap`, and `StepDescriptor.policies()` and `WorkflowDescriptor.policies()` give those attached, in order. A policy that defines no hook is refused when its descriptor is made.
- **A builder for each kind of policy**, for a class declared without decorators, as the plan's section 5, point 4 asks. `Audit.builder(name?)`, a static method of `StepPolicy` typed `this: C`, starts a `StepPolicyBuilder<C>`, in `src/policy/step-policy/builder.ts`, and `Notify.builder(name?)` a `WorkflowPolicyBuilder<C>`, in `src/policy/workflow-policy/builder.ts`; the name is the class's unless one is given. Each hook has a method of its own, such as `onStepSuccess(key, ...requests)`, naming the method of the class that implements it, typed `MethodKey<InstanceType<C>, OnSuccess>`, the keys of the methods returning what the hook may return or a promise of it, so a failure hook that may finish the workflow, a field or a missing method does not compile. Its requests are given by position, as a step's are (see [0062](0062-workflow-descriptors.md)). Each method checks at once what the decorators check when a class is defined, from `Hooks` in `src/policy/builder.ts`: a field holding a function rather than a method, a hook defined twice, a method given two hooks, a parameter with no request, and a cause the hook is not given. Starting a builder for a class declared with `@stepPolicy` or `@workflowPolicy` throws, saying to give the class itself, so that the two declarations of one policy cannot disagree. A step's builder takes either form in `policy(...)`, and the workflow builder likewise.
- **`hook defined twice`** is found when the workflow is built, with the other violations (see [0062](0062-workflow-descriptors.md)), by `src/workflow/violation/hooks.ts`: for each step, every policy attached to it that defines the same step hook, and for the workflow, every workflow policy that defines the same workflow hook, named in the order attached.

## Calling the hooks

Where each hook runs is in [0009](0009-running-a-workflow.md), and how one is called in [0002](0002-foundations.md). What is particular to this proposal:

- **`PolicyDescriptor.call(policy, hook, answers)`**, public, calls the method that implements the hook on a policy object the descriptor built, with the answers in order, and gives what it returned. It throws a `TypeError` when the object has no such method, which only a cast lets happen.
- **What a hook returned** is checked by `lifecycleOf`, in `src/engine/hook/lifecycle.ts`, whatever a cast let through: nothing, or `KeepDefault`, keeps the default; `FinishWorkflow` only from `on step success`; `FailWorkflow` with a reason whose code is a string and whose message is a string or absent, captured again as `failWorkflow` captures it, gives a frozen lifecycle of its own. Details that are not a value abort the journey with `not a value`, naming the step and the hook; anything else, any lifecycle from a workflow hook, or a getter that throws while it is read, aborts it with `invalid lifecycle`, naming the step of a step hook.
- **Roles.** A request `@role<R>()` is answered with the workflow object of the instance, which implements every role its policies request, as the types made sure.
- **Test support.** `stepPolicyMock(script)` and `workflowPolicyMock(script)`, in `src/testing/`, from `itinera/testing`, are policies whose hooks keep what each call received and end as the script says, through `HookEnding` (see [0108](0108-test-support.md)).
